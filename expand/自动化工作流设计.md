# 自动化工作流设计

> 为 `D:\note` 知识库搭建「采集→过滤→加工→入库」的全自动管线，按 `agents.md` 规则持续丰富知识图谱。

---

## 一、项目概述

### 1.1 目标

构建一条无人值守的知识自动化产线，每周自动从多个平台采集 AI / Agent / 后端开发（Java / Kotlin / Python）相关的最新内容，过滤噪音后按 `agents.md` 的 Ingest 规范纳入 `wiki/`，并在每日巡检中确保没有遗漏加工。

### 1.2 当前资产

| 资产 | 说明 |
|------|------|
| `raw/` | 原始素材库（只读，永不修改） |
| `wiki/` | 个人学习笔记（只读，仅用户修改） |
| `expand/` | AI 加工产物（条目 + 索引 / 图谱 / 日志） |
| `agents.md` | 规则文件（定义 Ingest / Query / Lint 流程） |
| 115 篇笔记 | wiki + expand 全部条目，已建立链接 |

### 1.3 工作流概览

```
┌────────────────────────────────────────────────────────────────────┐
│                        调度层 (cron / Task Scheduler)                 │
│                                                                     │
│   每周一 06:00  →  采集 + 过滤（全量抓取 → LLM 打分 → 入 raw/）       │
│   每天   08:00  →  巡检 + 加工（扫 raw/ 未处理素材 → 按 Ingest 入库）  │
│                                                                     │
├────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   采集层                            加工层（Agent）                   │
│   ┌─────────┐  ┌──────────┐       ┌──────────────────────┐         │
│   │ GitHub  │  │ RSSHub   │       │  读取 agents.md      │         │
│   │ API     │  │ 多源聚合 │──────→│  提取关键概念         │         │
│   ├─────────┤  └──────────┘       │  创建/更新 wiki 条目  │         │
│   │ HN/Reddit│                    │  建立 [[双向链接]]    │         │
│   │ JSON     │                    │  更新 index.md        │         │
│   └─────────┘                     │  追加 log.md          │         │
│        ↓                          │  验证并标记已处理      │────────→ wiki/
│   过滤层（LLM 质检）                └──────────────────────┘         │
│   ┌──────────────────────┐                                         │
│   │  相关性打分 ≥ 7/10   │── 通过 ──→ raw/                         │
│   │  垃圾/广告/水文       │── 丢弃                                  │
│   │  SimHash 去重        │── 跳过                                  │
│   └──────────────────────┘                                         │
│                                                                     │
└────────────────────────────────────────────────────────────────────┘
```

## 二、采集层

### 2.1 平台可行性分级

| 难度 | 平台 | 采集方式 | 说明 |
|------|------|---------|------|
| 🟢 容易 | **GitHub Trending / Search** | GitHub REST API + GraphQL | `topic:ai-agent topic:langchain` 过滤，stars>10 当日趋势 |
| 🟢 容易 | **HackerNews** | 官方 Firebase API | `hacker-news.firebaseio.com/v0/topstories` |
| 🟢 容易 | **Reddit** | 追加 `.json` 到任意 URL | `r/MachineLearning`, `r/androiddev`, `r/programming` |
| 🟢 容易 | **ArXiv** | API 搜索 | `cat:cs.AI` + 关键词 `agent|RAG|fine-tuning` |
| 🟢 容易 | **Papers With Code** | API | 按方法/任务获取带 GitHub 链接的论文 |
| 🟡 中等 | **CSDN / 掘金 / 知乎** | **RSSHub** | 自部署或使用公共实例，有各平台路由 |
| 🟡 中等 | **Newsletter** | 邮箱 + IMAP 抓取 | AI 日报/机器之心/量子位/AI 前线 |
| 🟡 中等 | **微信公众号** | 微信读书/WeRSS 第三方 | 国内 AI 领域公众号聚合 |
| 🔴 困难 | **B站 / 抖音 / 小红书** | **不建议自爬** | 反爬极严，建议改用 Newsletter 或关注 AI 领域博主动态 |

### 2.2 推荐入手顺序

```
第一阶段（2 天）          第二阶段（3 天）             第三阶段（持续）
───────────────────    ───────────────────    ───────────────────
GitHub Trending API    → RSSHub 国内聚合      → Newsletter 抓取
HN Firebase API       → 掘金 / CSDN / 知乎    → 去重优化
Reddit JSON           → ArXiv 论文          → 个人兴趣反馈调权
```

### 2.3 素材归档格式

每条采集内容存入 `raw/` 时使用统一格式：

```markdown
---
source: github
url: https://github.com/xxx/agent-framework
title: awesome-ai-agents
collected: 2026-08-03
status: pending
score: 8
tags: [langchain, agent, python]
---

# awesome-ai-agents

> [作者] 发布于 2026-08-01 | ⭐ 2341

原始摘要或正文内容...
```

- `status: pending` → 加工后改为 `status: processed`
- `score` 由过滤层 LLM 打分填充

## 三、过滤层

### 3.1 三级过滤管道

```
粗滤（关键词/规则）  →  精滤（LLM 打分）  →  去重（SimHash）
─────────────────    ────────────────    ──────────────
正则匹配：            LLM Prompt 模板：   内容指纹 + 标题对比：
- 必含 AI/Agent/      对以下内容评分...     已知 raw/ 中已存在?
  Java/Kotlin/Python/                        → skip
  Android/后端
- 过滤纯广告链接模式
- 过滤低质量域名
```

### 3.2 LLM 打分 Prompt 模板

```
你是技术内容审核助手。对以下内容进行 3 维度评分（每项 0-10）：

内容摘要：{summary}
来源平台：{source}
原文链接：{url}

1. 相关性 (0-10)：是否涉及 AI 应用 / Agent 智能体 / 后端开发 (Java/Kotlin/Python/Android)？
2. 技术深度 (0-10)：是否包含可操作的技术方案而非泛泛而谈？
3. 新鲜度 (0-10)：是否是新信息（相对于当前日期 2026-08-03）？

加分项：开源项目/可复现实验/有代码示例 +1
扣分项：纯标题党/纯广告/低质水文。是 → 总分清零

输出 JSON：
{
  "pass": true/false,
  "relevance": 8,
  "depth": 7,
  "freshness": 6,
  "total": 7,
  "reason": "开源 AI Agent 框架，含代码示例，相关性高",
  "suggested_category": "06-AI与LLM"
}
```

**阈值：`pass=true` 且 `total ≥ 7` 即入库 `raw/`。**

### 3.3 去重策略

| 方法 | 说明 |
|------|------|
| **URL 精确匹配** | `raw/` 中已有相同 URL → 直接跳过 |
| **标题相似度** | 用 TF-IDF + 余弦相似度，≥ 0.85 视为重复 |
| **内容 SimHash** | 64 位海明距离 ≤ 3 视为重复 |
| **GitHub 特殊处理** | 同一 repo 的新 release / 新 star 里程碑视为更新而非重复 |

## 四、加工层（对接 agents.md）

### 4.1 Ingest 自动化流程

按 `agents.md` 中的 **Ingest（摄入）** 操作标准，自动化执行：

```
触发：每日 08:00 扫描 raw/ 中 status=pending 的素材
     或手动执行 "摄入" 命令

Step 1  读取 raw/{素材}.md
        ↓
Step 2  LLM 提取关键概念、事实、见解
        判断应归类到 wiki/ 哪个分类（01-11）
        ↓
Step 3  检查 wiki/ 中是否有相关已有条目
        - 有 → 增量更新现有条目（追加内容到 ## 详细说明）
        - 无 → 创建新条目
        ↓
Step 4  建立双向链接 [[ ]]
        更新本条目 ## 相关条目
        更新被引用条目 ## 相关条目（加回链）
        ↓
Step 5  更新 wiki/index.md（追加/修改条目摘要）
        ↓
Step 6  更新 wiki/知识图谱.md（关联描述）
        ↓
Step 7  追加 wiki/log.md 变更记录
        ↓
Step 8  将 raw/ 素材的 status 改为 processed
```

### 4.2 Ingest 的 Prompt 模板

```
你是知识库管理助手。按以下规则将原始素材转化为知识条目：

## 原始素材
{raw_content}

## 知识库分类体系
01-编程语言 | 02-前端 | 03-后端 | 04-数据库 | 05-数据结构与算法
06-AI与LLM | 07-Linux与工具链 | 08-逆向与安全 | 09-源码解读
10-求职面试 | 11-生活杂项

## 规则（来自 agents.md）
- 个人手写笔记内容不可改写，只追加 ## 相关条目
- AI 生成的摘要性条目要简洁，用自己的话总结
- 积极建立双向链接 [[条目名]]

## 输出要求
1. 判断应归入哪个分类；分类无法对应时新建子目录
2. 如果该主题在知识库中已有条目：增量更新，不重复创建
3. 全新主题按**深度技术笔记模板**输出（见 agents.md，取代六维框架）：
   - 角色：资深架构师（Agent / Java/Kotlin 后端 / KMP / Android）
   - 规则：强制补全并深度融合（`[补充]` 标注）、人话解释、最小可运行代码示例（标注版本）、生产级考量、表格化排版
   - 结构：`## 本周主题` → 一句话总结 → 核心概念拆解 → 架构与方案对比 → 代码与实操速查 → 避坑清单 → 知识关联地图 → 素材盲区与知识增量 → 行动清单
4. 所有链接使用 [[文件名]] 格式，双向维护 ## 相关条目

输出为 Markdown 文件，不要输出 JSON。
```

### 4.3 增量更新策略

| 场景 | 处理方式 |
|------|---------|
| 新主题 → 知识库无相关条目 | 创建 `wiki/XX-分类/新条目.md` |
| 新素材 → 与某条目高度相关（相似度 > 0.6） | 增量更新该条目（追加段落到 ## 详细说明） |
| 新素材 → 仅补充了某个已有知识点 | 追加到 ## 相关条目 + 简短引用标注 |
| 新素材 → 与多个条目相关 | 创建新条目，并在多个已有条目中追加双向链接 |

## 五、巡检与 QA

### 5.1 每日巡检（Lint）

```
触发：每天 08:00（加工完成后自动执行）

检查项：
1. raw/ 是否有 status=pending 且 collected > 24h 的素材（漏加工）
2. wiki/ 是否有孤立节点（无任何链接的条目）
3. wiki/ 是否有断链（[[ ]] 引用不存在的目标）
4. wiki/log.md 是否自上次加工后无新增记录（加工失败标记）
5. raw/ 是否有 pending 素材超过 7 天未处理（积压告警）

输出：巡检报告 → wiki/log.md
```

### 5.2 质量指标

| 指标 | 含义 | 目标 |
|------|------|------|
| 采集量 (W) | 每轮采集素材数 | 5-30 条/轮 |
| 通过率 (W) | 过滤后通过率 | 20-50%（宁缺毋滥） |
| 加工量 (D) | 每日新增/更新条目数 | 0-5 条/天 |
| 积压率 | raw/ 中超过 48h 未处理的占比 | < 10% |
| 链接健康度 | 所有 [[ ]] 可解析 | 100% |
| 孤立率 | wiki/ 中无链接条目占比 | < 5% |

### 5.3 一致性门禁（Track 1：不变量检查 K1-K7）

> 目的：把「质量指标」从巡检报告升级为**提交断言**——知识库结构损坏时，本地提交与 CI 双双拦截，烂东西进不了库。

**检查清单**（`scripts/check_consistency.py`）：

| 检查 | 内容 | 失败时 |
|------|------|--------|
| K1 | raw/ 素材状态机合法（pending/processed/rejected，processed 须有 hash；存量放行） | 阻塞 |
| K2 | expand/index.md 声明的条目数与磁盘实际一致 | 阻塞 |
| K3 | expand/ AI 条目 frontmatter 字段完整（created/updated/sources/tags） | 阻塞 |
| K4 | 全库 `[[]]` 双链可解析，无死链 | 阻塞 |
| K5 | 所有条目均登记于 expand/index.md | 阻塞 |
| K6 | expand/ 必检 markdown 表格形状对齐 | 阻塞 |
| K7 | 孤立节点（无入链） | 仅警告 |

**两道闸**：

1. `.githooks/pre-commit`（本地）：staging 涉及 `expand/` `wiki/` `scripts/` `.githooks/` `.github/workflows/` 时运行 K1-K7，失败阻断 commit。启用：`git config core.hooksPath .githooks`
2. `.github/workflows/consistency.yml`（CI）：push main + PR 时运行，**job 名固定 `consistency / check`**，配合分支保护设为必需检查——本地钩子可被 bypass，CI 才是合并前真正的硬闸。

**工程经验**（Windows 钩子坑）：

- PS 5.1 `Set-Content -Encoding UTF8` 写 UTF-8 BOM，会破坏 `#!/bin/sh` shebang 导致 git `cannot spawn`——钩子必须 BOM-free 写入（`write` 工具 / `[IO.File]::WriteAllText`）
- Git for Windows 从 git 安装目录 spawn 钩子，**不要用 `$0` 或 CWD 推导仓库根**，用 `git rev-parse --show-toplevel`
- 中文文件名需 `git -c core.quotepath=false diff --cached --name-only`，否则路径被引号转义、case 匹配失效
- 钩子内 python 解释器探测回退：`python` → `python3` → `py`（Windows 无 `python3.exe`）
