## 一、项目画像摘要

OpenCode 是一个**开源 AI 编码助手（AI Coding Agent）**，以"AI 驱动的开发工具"为定位，提供终端 UI（TUI）、桌面端（Electron）、Web 端与在线控制台（Console）四种交付形态。整个仓库是一个 **Bun workspace + turbo 的 TypeScript monorepo**，包含约 32 个 workspace 包，核心采用 **Effect 函数式编程框架**构建，运行于 Bun 运行时之上。

### 核心业务链路

**用户输入 → Prompt 持久化准入 → Context Epoch 基线渲染 → Provider 轮次（单次 llm.stream）→ 工具调度与结算 → 响应投影 → Session 历史持久化 → UI 渲染**。整条链路围绕"会话（Session）"这一核心业务对象组织，Session 生命周期由 V2 Session Core 管理，严格区分**准入（admission）**与**执行（execution）**两个阶段。

### 核心业务对象

- **Session**：会话，系统主业务对象，承载全部对话状态与持久化历史
- **Context Source / Context Epoch**：上下文源与上下文纪元，管理模型可见上下文的不变基线与增量更新
- **Provider / Model**：模型提供商与模型目录（Catalog），负责多模型路由与协议适配
- **Tool / Tool Registry**：工具系统，含权限管控与输出截断
- **Agent / Skill**：智能体（build / plan / general 等）与技能体系

## 二、系统设计倾向

### 可靠性优先（Reliability-first）

与典型 Web CRUD 系统不同，OpenCode 的设计倾向是**可靠性优先**而非吞吐优先：

- **持久化准入**：Prompt 先落库（`session_input` 表）再调度执行，进程崩溃后可恢复续跑
- **Context Snapshot 原子推进**：上下文变更仅在安全边界（Safe Provider-Turn Boundary）惰性采样，保证模型输入的一致性视图
- **Unavailable Context 容错**：上下文源加载失败时采用 stale-while-revalidate，保留先前有效状态而非静默丢弃
- **Baseline 跨进程复用**：Baseline System Context 持久化存储，进程重启后原样复用，避免 token 重复消耗

## 四、系统优势板块

1. **会话编排架构**：V2 Session Core 的准入/执行分离、SessionRunCoordinator 并发协调、Compaction 压缩续跑，构成完整的编码 Agent 运行时
2. **上下文管理体系**：Context Epoch + System Context Registry + Context Source 的类型化设计，解决长会话上下文膨胀与一致性难题
3. **SDK 代码生成**：HttpApi → SDK Contract IR → Promise/Effect 双 Emitter，实现"一份协议契约，多运行时消费"
4. **Effect 函数式架构**：Service/Layer/Scope 全域落地，错误通道类型化，并发安全由框架保证
5. **多端一致性**：共享 Schema/Protocol/Client，TUI/Web/Desktop 体验一致

## 五、系统短板

1. **进程本地协调**：Session Drain 与执行协调为进程本地实现（源码明确标注"clustered 前保持本地"），不支持多节点集群化
2. **Session 状态持久化不完整**：busy/retrying/idle/interrupted 等运行态未做持久化（runner 源码 TODO 明确），进程重启后运行态语义丢失
3. **Provider 重试与重复工具调用无上界**：runner TODO 项"Bound provider retries and repeated identical tool calls"未落地
4. **SDK 双轨并存**：旧版 `@opencode-ai/sdk`（js/ 子目录）与 `@opencode-ai/sdk-next` 并存，迁移尚未完成
5. **缓存策略覆盖不全**：Cache Policy 仅对声明 RESPECTS_INLINE_HINTS 的协议生效（anthropic-messages、bedrock-converse）
