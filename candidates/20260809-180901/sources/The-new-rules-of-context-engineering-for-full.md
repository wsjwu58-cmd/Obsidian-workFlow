w-variant-41fc0c0a-cac3-53c9-9802-6a916e3fb342 u-ignore-trim"></div></div><div class="u-rich-text-blog u-margin-trim w-richtext"><h2>Then and now</h2><p>There were a number of previous context engineering best practices that had become myths. Including:.</p><figure style="max-width:2048pxpx" class="w-richtext-align-fullwidth w-richtext-figure-type-image"><div><img alt="" src="https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a63620bedb2b7813b107213_3979f6a1.png" loading="lazy"></div></figure><h3>Then: Give Claude rules</h3><h3>Now: Let Claude use judgement</h3><p>When we first rolled out Claude Code, we needed to be sure that Claude avoided worst case scenarios, such as deleting files. This meant we would give particularly strong guidance that might not always be true, For example, in the system prompt we used to say:&nbsp;</p><p><em>In code: default to writing no comments. Never write multi-paragraph docstrings or multi-line comment blocks — one short line max. Don't create planning, decision, or analysis documents unless the user asks for them — work from conversation context, not intermediate files.</em></p><p>But for a certain subset of prompts, this guidance would be wrong. In the case of documentation, the user may have their own preferences, or specific parts of very complex code might need multi-line comment blocks.</p><p>Still, without these guardrails for older models, the comments Claude wrote would be incorrect in many cases and we had to accept this tradeoff. But newer models have better judgement and can handle these decisions well without explicit rules.&nbsp;</p><p>In the new system prompt we say: <em>Write code that reads like the surrounding code: match its comment density, naming, and idiom.</em></p><h3>Then: Give Claude examples</h3><h3>Now: Design interfaces</h3><p>The number one rule for tool usage was to give Claude examples on how to use them. With our newest models, we’ve found that giving examples actually constrains them to a certain exploration space.&nbsp;</p><figure style="max-width:2048pxpx" class="w-richtext-align-fullwidth w-richtext-figure-type-image"><div><img alt="" src="https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a63620bedb2b7813b107216_c4fdec0d.png" loading="lazy"></div></figure><p>Instead of using examples, think more about the design of your tools, scripts and files- what parameters does Claude have and how can they be more expressive?&nbsp;</p><p>For example, in the Todo tool example, just listing status as an enumeration between pending, in_progress, and completed, hints to Claude about how to use it. The instruction on keeping one item in_progress helps define our requested behavior.</p><h3>Then: Put it all upfront</h3><h3>Now: Use progressive disclosure</h3><p>Because Claude Code was focused on coding, our system prompt included detailed information on how to do code review and verification. These were not always needed, but when they were, it was crucial information.</p><p>Since then, Claude Code has gotten very competent at using progressive disclosure- loading the right context at the right times. For example, we moved verification and code review into their own skills that Claude Code could selectively call.</p><p>But progressive disclosure is not just for skills, we also use it for tools. Some of our tools are ‘deferred loading,’ which means the agent must search for their full definitions using ToolSearch before using them. This allows us to have more tools (such as our Task tools) that don’t take up context until they’re needed.</p><p>The same can be applied to your own CLAUDE.md and Skill.md files. A common myth is that you want to make these a central repository for every known practice that you <em>might</em> run into, because Claude would not find it otherwise. Instead, <a href="https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code">consider having a tree of files that can be loaded at the right time</a>.</p><h3>Then: Repeat yourself</h3><h3>Now: Simple tool descriptions</h3><p>Earlier Claude models could sometimes need repeated instructions or be more likely to listen to instructions at the end of their context window than at the start. This meant our system prompt would sometimes have references to tools in the main system prompt as well as instructions in the tool description.&nbsp;</p><p>We found we could delete these repeat examples and put instructions on how to use tools in the tool descriptions rather than the system prompt.</p><h3>Then: Memory in CLAUDE.md files</h3><h3>Now: Auto-memory</h3><p>We used to encourage users to save things to Claude’s memory, by using the # hotkey to write to their <a href="http://claude.md/">CLAUDE.md</a> automatically. Instead, Claude now automatically saves memories that are relevant to the work and to you.&nbsp;</p><h3>Then: Simple specs</h3><h3>Now: Rich references</h3><p>In plan mode, Claude Code has heavily relied on markdown files with plans. Storing these files as plans helped Claude refer to them when needed. Another similar best practice was to store specs in the codebase for Claude to refer to while working across longer projects.</p><p>But we’ve found that Claude can handle increasingly more complicated references. Instead of simple markdown files, Claude can reference HTML artifacts created by our new artifacts feature.&nbsp;</p><p>You may also give Claude references in the form of code. A spec may also be a detailed test suite, or a function in a different codebase that Claude might port.&nbsp;</p><p>Rubrics are another form of references. Rubrics allow Claude to try and verify your taste in a particular field (e.g. what does a good API design look like) by using <a href="https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code">dynamic workflows</a> and spinning up verifier agents with those rubrics.</p><h2>Applying this to your context</h2><p>Pulling this all together, what does this look like when you assemble your context?</p><figure style="max-width:2048pxpx" class="w-richtext-align-fullwidth w-richtext-figure-type-image"><div><img alt="" src="https://cdn.prod.website-files.com/68a44d4040f98a4adf2207b6/6a63620bedb2b7813b10721a_836a850d.png" loading="lazy"></div></figure><h3>System Prompt</h3><p>A system prompt is heavily tied to the product context. It tells Claude what product it’s operating in and what it’s doing. For Claude Code, you will likely never modify this, but if you are building your own agent harness, this is where you should spend a lot of time.</p><h3>CLAUDE.md</h3><p>Keep your CLAUDE.md lightweight and briefly describe what your repo is for, but spend most of the tokens on gotchas inside of the codebase. For example, you may organize your code to keep types in one monolithic file and nowhere else. Avoid stating ‘the obvious’ things Claude should know by looking at your file system or your repo.</p><p>Use progressive disclosure heavily, for example if you have several unique instructions on how to verify your work, create a verification skill and reference it from your CLAUDE.md.</p><h3>Skills</h3><p>Think of skills as lightweight guides to let Claude find information when needed. Avoid making them overconstrained, except in highly important areas.&nbsp;</p><p>For long skills, try and use progressive disclosure as much as possible- divide it into many files and split them out.</p><p>It’s best when skills encode particular opinions, knowledge, or best practices that are particular to you, your team, or product.&nbsp;</p><h3>References&nbsp;</h3><p>You can @ mention files to include them as references. References allow Claude to refer to in-depth information about the current plan.&nbsp;</p><p>This might be in specs files, mockups, or even entire codebases. Generally you should prefer files that are in code as it provides clear, high-fidelity instructions to Claude in a language it knows very well. For example, a HTML mockup of a design will generally produce better results than a description of the design or a screenshot.</p><h2>Try simplifying</h2><p>Across your system prompt, skills, and CLAUDE.md files, you may need to simplify just like we did. We rolled out a new command called `claude doctor,` which will help you do this automatically as well. For more details on prompting more advanced models specifically, check out our <a href="https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns">Fable field
