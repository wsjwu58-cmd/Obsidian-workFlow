# 六种智能体编排模式

> [vercel.com/i](https://vercel.com/i/agent-orchestration-patterns)｜分类：Build with AI
> 来源：Vercel（Build with AI 指南）
> 发布：队列日期 2026-08-09（页面引用 2026-07 AI Gateway Production Index）
> 原文：https://vercel.com/i/agent-orchestration-patterns

一旦一个 AI 功能超出了单条提示词的范畴，决策就变成了：如何把大语言模型（LLM）调用连接成一个在生产负载下依然可靠的系统。正确的编排模式应当匹配任务的可分解性、延迟容忍度、token 预算，以及"人在环路中"（human-in-the-loop）的要求。先用能解决问题的最简模式，只有当负载确实需要时才升级。六种模式分别对应可靠性、成本与协调这三者之间的不同权衡。

**要点速览：**

- 多智能体系统的 token 用量可达标准对话的 15 倍，因此任务价值必须足以证明这份额外复杂度的合理性。
- 在等算力预算下，对 Qwen3、DeepSeek-R1 和 Gemini 2.5 的多跳推理任务，单智能体循环达到或超过多智能体的准确率。
- 提示链（prompt chaining）是单次 LLM 调用之上风险最低的升级，但链式准确率会逐步复合衰减。
- 编排者—工作者（orchestrator-worker）是为"编写时子任务数量与性质均未知"的场景设计的模式，因此它是多智能体工作的入口，而不是默认选项。
- Vercel Workflows 会对每一步做检查点并处理失败重试与外部事件暂停，因此六种模式都能持久化运行。
- FLORA 的创意智能体把单个会话扇出到 50 多个图像模型，每一步都持久化并在失败时重试。

## 智能体编排模式一览

在引入智能体之前，先从复杂度最低的模式开始。六种模式构成一道复杂度阶梯。过早扇出（premature fan-out）这一反模式，出现在团队在负载尚无独立子任务时就引入智能体的时候，它会同时放大成本与故障面。

多智能体系统的 token 用量大约是对话交互的 [15 倍](https://www.anthropic.com/engineering/multi-agent-research-system)，因此任务价值必须足以证明引入这些智能体的合理性。模式选择取决于负载，而不是团队的雄心。

六种模式在适用性、token 成本和失效条件上各不相同。在选定模式前，可把下表当作一个规划范围：

| 模式 | 最适合 | 相对单次调用的 token 成本 | 何时避免 |
| --- | --- | --- | --- |
| 单智能体循环（single-agent loop） | 能在单个上下文窗口内、带工具访问完成的任务 | 基线 | 能受益于并行探索的独立子任务 |
| 提示链（prompt chaining） | 编写时已知的固定子任务 | 中等，由链长固定 | 子任务边界未知 |
| 路由（routing） | 需要分别处理的不同输入类别 | 低到中等 | 需要完全相同处理的输入 |
| 并行化（parallelization） | 预定义的独立子任务 | 高，随扇出规模变化 | 存在顺序依赖或共享上下文 |
| 编排者—工作者（orchestrator-worker） | 直到运行时才能确定的子任务 | 高，随工作者数量变化 | 子任务可预测 |
| 评估者—优化者（evaluator-optimizer） | 有清晰评估标准、且迭代能带来可衡量收益 | 中等，随批评—修订循环次数变化 | 需要实时响应，或没有评估标准 |

这些范围是相对估算，锚定在已测量的智能体与多智能体 token 数据上。2026 年 7 月的 AI Gateway 生产指数显示，Anthropic 占 [AI Gateway 支出的 61%](https://vercel.com/blog/ai-gateway-production-index-july-2026)，却只对应 32% 的 token，可见最具分量的智能体工作高度集中了成本。在任何基础设施决策之前，先要在各种[智能体工作流模式](https://vercel.com/i/what-are-agentic-workflows)之间做出选择。

## 1. 从单智能体循环开始智能体编排

在等 token 预算下，[单智能体基线](https://arxiv.org/html/2604.02460v1)在多跳推理上达到或超过多智能体的准确率，而多智能体报告出来的优势，更可能由未被计入的计算量而非架构本身来解释。

同样的约束在生产中也会出现。复杂度更低的架构能带你走得很远，而并行写作仍会撞上协调与上下文共享的约束。升级应当跟随一个具体的能力缺口，例如上下文窗口压力，或确实能并行运行的独立子任务。

单智能体循环是一个 LLM 调用工具、接收结果、把结果加入上下文，然后重复，直到满足停止条件。在 AI SDK 7 中，[`ToolLoopAgent`](https://ai-sdk.dev/docs/reference/ai-sdk-core/tool-loop-agent) 运行这个循环，并通过 `stopWhen: stepCountIs(20)` 默认在 20 步后停止。`prepareStep` 回调可以在步骤之间调整模型、工具、消息和运行时上下文。AI SDK 7 还新增了带类型的 `runtimeContext`、智能体级工具审批，以及总量、单步、单块和单工具的超时。状态管理问题——包括重复的账号编号和重复运行的搜索——会把团队推离这个模式。`WorkflowAgent` 把该循环拆成一次次独立的调用，因此已完成的步骤永远不会重跑。

## 2. 用提示链处理固定的智能体编排步骤

提示链运行一个固定的 LLM 调用序列，每一次调用处理上一次的输出。提示链适合具有固定分解方式的任务。它通过收窄每次调用的范围，用延迟换取准确率。准确率会在各步骤之间复合。若每步准确率为 95%，走十步后端到端准确率约为 60%；若为 90%，则约为 35%。

正是这种复合效应，使得步骤之间的程序化关卡（gate）不是可选项。关卡可以在下一次调用继承一个糟糕的中间结果之前，检查模式有效性、必填字段、策略阈值或人工审批。Vercel 内部的数据智能体 d0 在生产中运行着持久化的多步编排。

AI SDK 负责它的模型调用，而 [Vercel Workflows](https://vercel.com/docs/workflows) 在 Snowflake 超时或模型调用失败时补上重试与状态恢复，并暂停一个必须等待人工或 webhook 的运行。当子任务边界在编写时未知，或独立子任务本可以同时运行时，就跳过链式编排。

## 3. 按输入类型路由智能体编排

路由增加一个初始分类步骤——可以基于 LLM，也可以是确定性的——把每个输入指派给一个专门的下游处理器。它分离关注点，在"不同类别最好分开处理"时奏效。路由器的准确率会给整个系统设定上限，因为一个被错误分类的输入会把错误的工作送给专门处理器。

只要输入空间允许，就优先用确定性分类器（正则、关键词匹配、基于规则的路由），因为它们能彻底消除一个模型失效面。路由还需要一个能反映生产输入的验证集，因为纸面上干净的分类法并不保证边界处的可靠分类。

在模型层面，[AI Gateway](https://vercel.com/docs/ai-gateway) 通过单一端点在上百个模型之间路由。它处理自动故障转移与负载均衡，并支持按提供商回退。Okara 在这一层为 [120,000+ 家企业](https://vercel.com/customers/how-okara-runs-cmo-agents-for-120000-companies-on-vercel)运行首席营销官（CMO）智能体；在把重试与回退处理迁移进网关后，它现在每天处理 40 亿 token。当每个输入都需要完全相同的处理、或无法验证分类准确率时，就跳过路由。

## 4. 为独立子任务运行并行智能体编排

并行化同时运行独立的子任务，并以程序化方式聚合它们的输出。它使用预定义的子任务，而编排者—工作者则在运行时确定子任务。当子任务可以同时运行以换取速度，或当针对同一任务的多种视角能提升结果置信度时，该模式适用。聚合步骤应当在扇出开始之前就定义好，因为不一致的工作者输出可能在合并时抹掉延迟收益。

AI SDK 把一个[子智能体](https://ai-sdk.dev/docs/agents/subagents)表示为一个通过父智能体工具来调用的智能体。每个子智能体接收自己的上下文窗口，并向父智能体返回一个聚焦的结果，从而把上下文繁重或并行的工作挡在主智能体的历史之外。子智能体会增加延迟与协调成本，因此只在上下文隔离或并行执行能带来可衡量收益时才使用它们。

在大规模扇出中，计费与代码同等重要，因为每个并发调用一生中大部分时间都在等待模型调用。FLORA 的创意智能体从单个会话扇出到 50 多个图像模型。[Fluid compute](https://vercel.com/docs/fluid-compute) 按活跃中央处理器（CPU）计价，因此等待模型调用不计入该计量。当子任务必须按顺序相互依赖、或需要一个共享上下文时，就跳过并行化。

## 5. 为动态分解选择编排者—工作者智能体编排

在编排者—工作者模式中，一个中央 LLM 在运行时确定一个请求需要哪些子任务，把它们指派给工作者智能体，并综合结果。用 AI SDK 时，每个工作者都可以实现为一个子智能体，通过工具暴露给父级 `ToolLoopAgent`。工作者在隔离的上下文中运行，并返回一份摘要结果供综合。它适合子任务无法预测的复杂任务，比如编码——要改多少个文件取决于请求本身。对其他任何场景来说它都是过度设计。每个工作者持有自己的上下文窗口，这意味着协调在带来能力的同时也增加了成本。

General Intelligence 的 Cofounder 为创始人提供一支覆盖工程、营销、搜索引擎优化（SEO）、财务、销售、客户支持与运营的完整智能体团队，形态与编排者—工作者一致。其工程师每人每天交付 [10 个拉取请求](https://vercel.com/customers/how-general-intelligence-used-agents-to-build-an-agent-platform-on-vercel)（PR）和 70+ 次提交，横跨 4,000+ 个预览分支，90% 的站点可靠性工程（SRE）工作已自动化。工作者代码在 [Vercel Sandbox](https://vercel.com/docs/sandbox) 微虚拟机中隔离运行，拥有独立的文件系统与网络。当子任务可预测、或协调开销超过动态分解的价值时，就跳过该模式。

## 6. 在质量可衡量时应用评估者—优化者智能体编排

评估者—优化者在循环中配对两次 LLM 调用。一次生成响应，另一次评估它并给出反馈，循环持续到达到质量阈值或步骤上限。该模式需要清晰的评估标准和迭代优化带来的可衡量收益，因此只有当响应在批评下确有改进时，它才值回成本。

有两个信号会让适用性更强：当人类能清楚说出有用反馈时响应会改善，以及 LLM 自己也能提供有用的反馈。失控的批评循环（runaway critique loop）反模式，出现在标准含糊、不断要求修订却看不到可衡量终点的时候。当首次尝试的质量已满足要求时，就避免该模式，并在应用代码中强制设置一个硬性的修订上限。对于基于智能体的实现，AI SDK 暴露了 `stopWhen` 条件和 AI SDK 7 的超时预算，用来约束总体与单步执行时间。

[Vercel 的 Turborepo](https://vercel.com/solutions/turborepo) 性能优化工作，就是这个批评循环的人在环路版本。AI 智能体、Vercel Sandboxes 与人工审查历时八天，带来了最高 [96% 的提速](https://vercel.com/blog/making-turborepo-ninety-six-percent-faster-with-agents-sandboxes-and-humans)；同一项工作还发现，缺少上下文工程、无人值守的最先进智能体表现不及预期。

Vercel 的 Next.js 智能体评测发现，在 Next.js 16 API 上 `AGENTS.md` 优于 skills。Vercel Sandbox 把每次隔离运行的上限设为 Hobby 45 分钟、Pro 与 Enterprise 24 小时，这也限制了批评循环能执行多久。

## Vercel 如何在生产中运行这些智能体编排模式

这六种模式是架构决策，但有四项平台行为消除了会在它们之间叠加放大的故障模式。在实践中，它们针对不同形态的工作处理相同的运行时关切，包括状态恢复、模型选择、扇出成本与隔离执行。

### Fluid compute 降低扇出步骤中的活跃 CPU 成本

并行化与编排者—工作者会扇出到许多由 I/O 等待主导的并发调用。团队必须拒绝任何为这种等待计费的计费模型，因为它会让大规模扇出变得不切实际。Fluid compute 以每小时 [$0.128 的基础费率](https://vercel.com/docs/functions/usage-and-pricing)单独计量活跃 CPU，区域费率与其他计量资源仍照常适用。

### Vercel Workflows 让每种模式都可持久

当运行中途状态丢失时，链式、编排者—工作者和评估者—优化者都会付出高昂代价。`use workflow` 指令把异步的 TypeScript 函数变成带检查点和重试的持久化工作流。运行也可以暂停与恢复，因此失败的运行会从上一个完好的步骤继续。Pro 与 Enterprise 上的工作流步骤支持最长 1,800 秒的执行时长。

### AI Gateway 在各类模式间集中模型路由

路由与编排者—工作者会依据任务需求和提供商健康状况选择模型，而成本约束则塑造回退策略。逐个提供商的集成工作会拖慢产品工作。AI Gateway 把这些整合成一个统一端点，带有重试与负载均衡，外加可配置的回退和对 token 零加价。提供商集成活在网关里而不是应用代码里，因此团队可以采用新上线的模型，而不必为每个提供商路径重新搭一遍。

### Vercel Sandbox 隔离工作者与评估者的执行

编排者—工作者和评估者—优化者模式会在编码智能体工作负载中运行生成代码或不受信任的代码。编码智能体需要这种隔离，之后才能安全地对准真实代码仓库。每个 Vercel Sandbox 都是一台 Firecracker 微虚拟机，拥有自己的文件系统与网络，而 `Sandbox.fork()` 从共享快照创建隔离分支。每个智能体还可以作为自己的 Linux 用户运行，拥有私有的 home 目录，而分组允许在智能体之间共享选定文件。当追踪横跨编排者与工作者时，会话关联把它们链接成单一连通视图。

## 让编排模式匹配你的负载，然后发布

主要风险来自选择了一个 token 成本或运维复杂度超过任务价值的模式。要为具体的能力缺口而升级，比如任务不再能塞进一个上下文窗口。Vercel 在单一基础设施栈上支持全部六种模式：

- **持久化编排：** Vercel Workflows 为每一步建立检查点，因此任何模式在失败时都不会从零重来。
- **活跃 CPU 计费：** Fluid compute 把模型调用的 I/O 等待排除在活跃 CPU 计量之外，这让扇出模式更可行，同时其他计量资源仍照常适用。
- **统一模型路由：** AI Gateway 在同一个路由层上处理自动故障转移，把逐个提供商的集成从应用代码中移除。
- **隔离代码执行：** Vercel Sandbox 在 Firecracker 微虚拟机中运行工作者与评估者代码，并配有有界的执行窗口。
- **端到端可观测性：** [OpenTelemetry](https://ai-sdk.dev/docs/ai-sdk-core/telemetry) 会话关联在一个视图中链接横跨编排者与工作者智能体的追踪。

部署一个[新项目](https://vercel.com/new)从单智能体循环开始，或者从 [Vercel 模板](https://vercel.com/templates)起步，只在负载需要时才升级模式。让第一版保持任务所允许的尽量小，等负载证明了需要，再添加协调。

## 关于智能体编排的常见问题

### 编排者—工作者与分层多智能体模式有何区别？

主管（supervisor）在预先定义的专家名册之间路由，并控制通信流。编排者则在运行时推导出子任务本身，并把它们委派给工作者智能体。

### 什么时候该用单智能体循环而不是多智能体编排？

当任务能塞进一个上下文窗口、子任务无法拆分并行运行、并且延迟或 token 预算紧张时，就用单智能体循环。只有当具体的能力缺口使多智能体编排成为必要时才升级。

### token 成本如何随智能体编排模式扩展？

token 成本会随着你增加模型调用、工作者、批评循环和独立上下文窗口而扩展。把表中的相对倍数当作规划范围，而不要把任何一种模式视为固定价格。

### 在智能体编排语境里，是什么让工作流变得"可持久"？

持久化执行会在每一步之后为状态建立检查点，因此链中途的失败会从上一个成功步骤恢复。Vercel Workflows 用 `use workflow` 指令实现持久化，因此一次运行可以为 webhook 或人工审批暂停而不占用计算，并从上一个检查点恢复。
