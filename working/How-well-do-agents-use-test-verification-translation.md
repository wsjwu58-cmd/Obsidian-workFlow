# 智能体在使用测试与验证技术方面表现如何？

[我们此前指出](https://danluu.com/ai-coding/)：一边是让编码智能体采用有效的测试技术、达到某个质量门槛比以往任何时候都容易，另一边软件质量却似乎在变差——这说明开发者正在使用的默认做法可能效果不佳。本文要检验的是：给智能体一些简单指令、要求它使用特定技术或库，能否提升实现的正确性。这本身也是一种检验——看看当指导者是一个对测试毫无专长、只是「大概听说过应该用某些技术或库」的人时，智能体到底能有多有效。

我们将复用[在《智能体编程语言有效性对比》中讨论过的 Zstd 实现评测](https://danluu.com/pl-tokens/)，改为在「实现 Zstd」的提示后追加不同附录（例如「使用测试驱动开发」「使用 Lean 4」「使用 QuickCheck」「使用基于属性的测试」等），来对比不同的测试技术与测试库。我还跑了一些别的评测，比如针对 IMAP RFC 的评测，文中会简要讨论。

所有实现都用 Rust 完成。测试了 26 种提示条件：ACL2、Alloy、「审计并模糊测试高风险区域」、「先审计」、Creusot、Default（不加任何额外指令）、差分测试、模糊测试、Hegel、Insta、Judgement（要求智能体自行判断并使用最佳技术）、Kani、Lean 4、「不要犯错」、蜕变测试、变异测试、基于属性的测试、Proptest、QuickCheck、rstest、Rust 内置测试框架、SMT 求解器（Z3、cvc5、Yices 全都可用）、Spin、TDD、TLA+、Verus。此外还测试了 4 种 skill：Hegel 配合[官方 Hegel skill](https://github.com/hegeldev/hegel-skill/blob/ef36dc6b26a6dc0fdfdab5476b1affff37552ef0/skills/hegel/SKILL.md)、[ECC Rust 测试 skill](https://github.com/affaan-m/ECC/blob/e04ea0b9cc8248686edf5ac751cadff550e162b8/skills/rust-testing/)（ECC 是一个 skill 合集，拥有 25 万 GitHub star、3.8 万 fork）、[Trail of Bits 属性测试 skill](https://github.com/trailofbits/skills/blob/d3323cefbcf645678b8dc481de204b02ad3d02dc/plugins/property-based-testing/skills/property-based-testing/SKILL.md)，以及我自己写的一个测试 skill（我是个老古董，用提示词而不用 skill，也完全不知道怎么写一个好 skill）。除我自己的 skill 之外，其余 skill 之所以入选，是因为它们是让 codex 去找相关 skill 时排名最靠前的几个。

### 预测

我预先登记了一些对各个条件表现的猜测：

- **TDD 会表现不佳**（55% 信心）。我特地加入 TDD，正因为我认为它会表现不佳。
- 这里信心很低，因为我不知道智能体在被要求做 TDD 时究竟会做什么；也许智能体不会真的做 TDD，而是做点不会拖后腿的事（又或者我对 TDD 表现不佳的判断是错的）。
- **形式化方法不会超常发挥**（52% 信心）。我的想法是：形式化方法确实有效且有用（如今比以往更甚），但好的测试方法同样有效且有用；在简单问题上，如果两者运用水平相当，形式化方法不应表现更好。
- 与上一条相同，且更甚：我的信心很低，因为我不知道智能体在被要求做任何事时会做什么；而且在智能体编程领域，形式化方法被炒作的程度超过有效的测试技术——所以完全有可能，各实验室用合成数据、在 RL 环境里训练智能体，把它们训练得非常擅长形式化方法，却没有训练它们有效掌握好的测试技术（我本以为后者更容易做到，但因为有效的测试技术相对不那么时髦而没人做）。
- **「不要犯错」不会胜过「不加指令」**（95% 信心）。这是个玩笑，而且很多人已经试过了。如果它有用，人们肯定早就注意到了吧？
- **ECC 测试 skill（25 万 star、3.8 万 fork）不会超常发挥**（65% 信心）。它有点大，而且其中没什么我认为有用的信息。它要求智能体使用 TDD；只要它能让智能体去做 TDD，我就觉得结果会更糟（而且它比单纯的 TDD 条件更具指令性，也许更可能奏效，不过据我所知，这反而可能让它更不可能奏效）；其余信息似乎没用，还带来了一些成本。
- 我对所有 skill 的预测信心都很低，因为我不太使用 skill，也不知道怎么真正评估它们。我的思考方式是：「如果我把这些文本当作提示词传进去、让它飘在 LLM 的上下文窗口里，它能有多有效？」
- **Hegel 的 skill 不会超常发挥**（65% 信心）。它非常大（SKILL.md 加上链接的 Rust 参考超过 2 万 token），读起来更像教程而不是给智能体的指令。
- **Trail of Bits 的测试 skill 不会超常发挥**（55% 信心）。它看起来可能包含一些有用的信息，但也相当大。

### 总体结果

下面这张图非常杂乱，展示了所测各条件的结果（codex 配 GPT-5.6 Sol，medium 与 xhigh 两档 effort）。看数据时，我比大多数人更偏爱信息密集、杂乱的图，[比如这里的第一张图](https://danluu.com/android-updates/)。由于大多数人觉得这类图乱得没法看，我在向他人展示信息时通常会把内容拆成一系列信息更少的图。但出于下面要讨论的原因，这次我不打算这么做，而是直接给一张极其杂乱的图：x 轴是成本，y 轴是 100% 通过（隐藏）测试的运行占比，每条件、每档 effort 取 80 次运行的均值（悬停会显示 bootstrap 协方差、[50% 不确定区间](https://statmodeling.stat.columbia.edu/2016/11/05/why-i-prefer-50-to-95-intervals/)，并对同类条件做了近似配色，例如形式化方法偏蓝、基于属性的测试偏绿等）：

> **交互式散点图**：`平均成本 vs. Zstd 满分运行占比（按测试条件与 effort）`｜来源：<https://danluu.com/interactive/agentic-testing/average-cost-vs-perfect-37.html>

我们能看到的一点是：**没有哪个条件大幅胜出。反而是 Default（不加任何额外指令）明显高于平均**。看 xhigh，平均而言，模糊测试和基于属性的测试（PBT）类的条件比形式化方法略好一些，而 medium 上的情况要混杂得多。codex 推荐的测试类 skill 表现不佳，不过我们临时自制的 skill 表现还行（一个主要区别是：我们的 skill 旨在把智能体从默认行为推离、推向更有产出的行为，而其他 skill 更像是教程）。TDD 表现不好，正如预测（有个 skill 也建议智能体使用 TDD，而它在智能体尝试遵循该指令的那些案例里表现也很差）。

如果我们真正去看智能体做了什么，很快就会明显发现：总体而言，**智能体并不知道如何很好地使用这些工具或技术**。[正如我们在此指出的](https://danluu.com/ai-coding/)，也正如我交谈过的每个人都注意到的那样：智能体非常不擅长测试，而且在「默认」情况下似乎并不理解如何合理地测试。例如，[Gary Bernhardt 的这条评论](https://x.com/garybernhardt/status/2067002665427775613)：

> AI 智能体对待测试的方式，大致是：把 15 年前某个反对 mock 的人凭空想出的病态案例拿过来——尽管自己从未真正用过 mock；把过度 mock 的那些病态做法当成你测试策略的骨架。

事实证明，如果你要求智能体使用某种特定的测试技术或测试库，它的做法并不会像你期望的那样有多少改变。稍后我们会更详细地看各个案例里发生了什么，但从高层看，面对测试技术，智能体要么只是把平时会写的测试塞进一个「另一种测试技术」的框架里，要么就表面化地用一下某种技术，却并没有真正做那些能让该技术产生价值的事。大多数情况下，当某个技术被点名时，它们只是把 Gary 描述的那套做法套用到该技术上（比如对形式化方法，它们大多证明一些无关紧要的性质；对基于属性的测试，智能体会严重依赖完全随机的输入，大量撞上无效/拒绝分支，或者找一个平凡的性质，然后对它跑一些低价值的随机用例）。在 IMAP RFC 上（每个条件跑了 40 次）结果没有实质不同，在其他随机的 RFC 上也一样（各跑了几次）。总体而言，无论问题类型是什么——是像 Zstd 这样的位操作问题、像 IMAP<sup>[1](#fn:I)</sup> 这样的协议，还是别的什么——智能体都没有有效地使用形式化方法、测试库或技术。

在 xhigh 上，智能体通常能让他们自己写的测试通过，但他们写的测试很差（例如，他们会给一个「使用四个比特流」的特性测试塞进四个完全相同的比特流，从而漏掉任何因比特流错位而引发的 bug）。[正如我们此前在 Zstd 评测中关于语言的讨论](https://danluu.com/pl-tokens/#appendix-medium-in-a-loop-vs-ultra)：在朴素循环里以更低的 effort 运行，结果会更差（智能体更频繁地这么做，并因正确率更低而卡住）。

我很想知道，为什么 AI 实验室还没建一些 RL 环境来让智能体学会如何好好测试——毕竟软件不能正常工作，对编码智能体的普及来说似乎很重要，而且这看起来也很适合用 RL 来做。[正如我们此前看到的，智能体已经在有界的运行时优化问题上变得相当擅长](https://danluu.com/perf-opt/)——这很合理，因为那正是你可以便宜地大量生成 RL 环境来训练的题目类型。也许这件事比看起来更难，但为有效的测试和测试技术创建 RL 环境，似乎属于同一类问题。也许限制因素只是[有效的测试技术](https://danluu.com/testing/)知识不够普及，所以没人想到去试，人们还在让智能体低效地测试（例如，做标准的单元测试）<sup>[2](#fn:U)</sup>；又或者，出于某种原因，这个问题比运行时优化更难打包？如果智能体变得足够好，以至于无需测试或验证就能一般性地写出正确代码，这个问题也许很快就会变得无关紧要；但至少从公开可用智能体诞生到现在的这段时间里（截至 2026 年 9 月），智能体若能对「如何在没有测试专家指导的情况下测试」有所概念，似乎本会大幅提升智能体编程的有效性。

下面我们会看看每个条件下智能体是怎么做的，按正确率从差到好排列；但我要提醒任何人，不要从这个排序里得出任何强结论。

这里的许多失败，看起来都与我们考察[编程语言对 token 用量和正确性的影响](https://danluu.com/pl-tokens/)时看到的失败类似——失败往往是特质性的（idiosyncratic）。例如在编程语言上，我们看到智能体在 Clojure 里把字节转换语义搞错的比率相当高，而在 Java 里则没有，尽管智能体「应该」（而且大概多少也确实）知道可以通过 `unchecked-byte` 而不是 `byte` 来获得 Java 的字节转换语义。

虽然人们对「为什么某些语言对智能体更好」有各种各样的高谈阔论，但当我们看智能体实际做了什么、失败模式是什么时，我听过的那些解释——无论是说 Elixir、OCaml 还是 J——没有一条是真的（例外是关于 Rust 内存安全的说法，[它在我们比较智能体编写的 C、C++ 与 Rust 的多语言 pandoc 评测中得到了证实](https://danluu.com/pl-tokens/#appendix-more-details-on-zstd)）。相反，我们看到一堆原因不明的特质性失败<sup>[3](#fn:P)</sup>。在语言问题上，由于我们能观察到语言流行度与性能（既包括更低成本、也包括更高正确率）之间有中等程度的相关性，可以合理猜测原因是流行语言有更多训练数据（可能不只是人类写的代码，也包括合成数据）。而在这里，并没有清晰的模式，只有一个例外：**当智能体手上只有一个库或技术的名字时，它们大多并不擅长应用测试或验证技术**（我们稍后会讨论什么方式更有效）。如果你不想读每个条件里发生了什么，[点此跳到最后一节](#skill)。

### Verus

[Verus](https://github.com/verus-lang/verus) 使用 SMT 求解器以及多种推理方式，来证明代码符合规格。

尽管 Verus 能证明代码符合规格，智能体并没有这么做。相反，它们证明了各种与 Zstd 相关的抽象性质。我自己没用过 Verus 这类工具，所以说不出一个专家、甚至一个初学者通常该怎么做；但读教程后我觉得有点奇怪：智能体没有尝试用 Verus 去验证任何实际代码，只把它用于抽象推理，而 Verus 的设计似乎就是为了让证明实际代码的性质变得容易。

此外，如果看它们证明的性质，通常证明的数量很少，而且证明的性质也没什么意思。比如智能体会证明「给定一个有效的游标/索引/距离，结果操作仍在边界内」这类东西——证明这个不算坏，但它并不是 bug 的来源。智能体还经常写出本质上等价于 `A => A` 的空洞证明。一个真实的 Verus 证明长这样：

```
requires
      0 < a <= window,
      0 < b <= window,
      0 < c <= window,
  ensures
      0 < c <= window,
      0 < a <= window,
      0 < b <= window,
```

在智能体确实证明了某些东西的情况下，它们一般也只会证明相对简单的东西，并回避那些很可能藏有 bug 的部分（例如，智能体经常忘了在编码和解码之间反转比特流顺序，并写出无法检出该问题的测试，因为这些测试是回文的；也许这里某种关于「反转」的证明能让智能体以不同方式去「思考」这一点）。

看来，只提供 Verus 和 Verus 文档，并不能让智能体从中获得价值。

如果看结果，Verus 在 xhigh 上的总体结果还行（正确率略低于平均，但便宜得多）。medium 的结果成本居中，正确运行占比最低，平均正确测试数也最低。因为智能体并没有真正从 Verus 中获益，它们实际用于保证正确性的手段主要还是传统测试（Rust 内置的 `#[test]` 单元测试）。从 medium 到 xhigh 时，智能体在传统测试上投入了多得多的精力，而只多用了一点点 Verus，这让 xhigh 的结果还算过得去。

看实际测试，对于 Verus 智能体做得差很多的两个特性之一（[四流跳表](https://github.com/facebook/zstd/blob/dev/doc/zstd_compression_format.md)），Verus 智能体在 160 个案例中有 89 个为它写了测试，巧合的是这与 Default 智能体的数字完全相同；但 Verus 智能体写出坏测试的可能性大得多。它们更可能把错误结果写进测试，也更可能写一些容易通过、覆盖空间很差的测试，比如让全部四个流都相同。这种情形就是我所说的「特质性失败」。并没有什么关于 Verus 的东西，使得人在不用 Verus 时就会写差测试；我们一般也不会指望一个用过 Verus 的人写出差的单元测试，就像不会指望一个用 Clojure 的人犯更多字节转换错误一样——但不知何故这里就是发生了（也许是巧合）。

我不知道 AI 实验室内部的人能否获得更好的信息来解释这些现象，但在外界，通常很难判断像这样的事为什么会发生（即便是我们对语言问题形成了看似合理的假设，那也需要跑很多语言的很多样本；而我们看过的、研究同一问题的论文之所以没有观察到「语言流行度 / 智能体有效性」的相关性，要么是因为它们考察的语言太少，无法推断出这么弱的相关性，要么是因为它们研究的问题太小、太琐碎）。

### Alloy

Alloy 常被称为有界模型检查器。到了 Alloy 6，这个说法可能不太准确了，因为它引入了一些额外特性，但这完全超出我的专业范围。我的理解是：用 Alloy 时，你通常证明的是关于你**模型**的性质（而不是证明你的代码能工作）。

Alloy 得了第二差的正确率，而且不同寻常的是，它在 medium 和 xhigh 上都普遍表现糟糕。虽然没有展示出来（因为似乎没什么增量信息），但总体而言，max 与 xhigh 的结果高度相关，而它们与 medium 的结果差别相当大。

正如我们在 Verus 上看到的，使用 Alloy 的智能体几乎完全依赖标准的 Rust `#[test]` 来保证正确率，大部分时间只是在 Alloy 上瞎折腾。再次说明：糟糕地使用形式化工具，对正确率没有帮助。

有个别 Alloy 的使用案例接近发现某个问题或风险，但即使如此，也只是少数。在一个案例中，Alloy 找到了一个反例，于是智能体在 Rust 实现里加了一个缓解措施来应对潜在 bug。不幸的是，那个反例依赖一次 8 位溢出，而这在实践中不可能发生，因为实际实现使用的是 64 位 `usize`，在给定输入下不可能溢出——所以它只是让代码更复杂，并没有预防真正的 bug。

另一个案例中，Alloy 规格本身是错的，一个相关测试失败了。测试失败后，智能体修正了 Alloy 规格。如果规格本来是正确的话，也许智能体能不经过这次失败就写出正确代码。有些案例里或许发生了「好的那一版」情形，但是否真的预防了一个潜在 bug 并不清楚。

Alloy 智能体建模的东西，确实比 Verus 智能体（后者大多只检查算术之类）更贴近 Zstd 算法，但仍然建错了模型。

### 差分测试

差分测试是这样一种技术：把相同的输入喂给多个实现，再比较结果以发现问题。原则上，这似乎很适合拿 LLM 来试——因为我们从不同的「掷骰子」中经常得到不同结果；而且[正如我们在此指出的](https://danluu.com/pl-tokens/#appendix-medium-in-a-loop-vs-ultra)，让智能体在一个实现上反复迭代（哪怕只是整个东西的一部分、甚至只是一个函数的一部分），通常比让它从头重来效果更差。

但这给了我们第三差的结果。此条件在 xhigh 上略高于平均，在 medium 上则远低于平均。没有一个智能体写出两份完整实现来对比。160 次运行中有 135 次做了某种勉强称得上差分测试的事，但正如我们见过的其他条件，这些测试普遍很琐碎、实际上没什么用。而且，在本该由差分测试抓住 bug 的情况下，智能体不是用相互独立的方式实现，而是把同一件事做了两遍，然后把同一个 bug 编码进了两份版本里。

我有时会让智能体独立做事、并用单独的上下文启动它们，但差分测试这里并没有有效地做到这一点——智能体通常只是把同一件事写了两遍。

### Hegel Skill

讨论官方 Hegel skill 如何改变 Hegel 行为是有意义的；但按正确率倒序排列，Hegel Skill 排在 Hegel 之上，因为它的正确率结果更差。关于这个 skill 的讨论见下面的 Hegel 一节。

### Lean 4

Lean 4 也许可以描述为[一个交互式定理证明器](https://en.wikipedia.org/wiki/Proof_assistant)。

虽然我没有为 Lean 预先登记预测，但如果我预先登记了「哪些形式化工具会表现好」的猜测，我会把 Lean 列进去，因为它相对热门/时髦，因而更可能因 RL 环境产生的合成数据而表现良好。

Lean 智能体确实证明了性质；和 Verus 条件一样，它们大多做的是算术证明，没有触及容易出错或高风险的部分。

和其他形式化条件一样，Lean 智能体严重依赖标准 Rust 测试。正如到目前为止的形式化条件一样，证明一些无关紧要的东西并没有帮助提升正确率。

### QuickCheck

QuickCheck 是[一个基于属性的测试库](https://en.wikipedia.org/wiki/Property_testing)，大概是这类库中长期最知名的，尽管如今 Hypothesis 可能占据了这个位置。

不幸的是，智能体使用基于属性的测试的水平，和它们使用我们前面看到的那些形式化工具的水平差不多。使用 QuickCheck 时，智能体大多写非常简单的「冒烟测试」，几乎不检查什么。它们还使用随机输入——在完全随机的情况下，这对测试 Zstd 这类东西相当糟糕（因为这些输入只会走进少数几条失败/拒绝分支）。

此外，被检查的性质也相对很少。虽然所有智能体都用了 QuickCheck，但 160 次运行中有 63 次只检查了单个性质。智能体再次主要依赖传统测试，尽管它们在技术上确实用了 QuickCheck。不知何故，智能体实际写的传统测试比 Default 或大多数其他条件都多，但测试-修复迭代更少（这使得该条件成本低于平均）。

### TDD

TDD 在这里也和 IMAP RFC 评测里一样表现不佳。

TDD 提示似乎引起了智能体行为的巨大变化。智能体产出的测试数量翻倍，并以一种测试-编码-测试-编码的迭代工作流工作，尽管一个 TDD 拥趸大概会说智能体并没有真正采用 TDD。只有少数几次智能体做了某种细粒度的迭代式 TDD。

总体而言，智能体前置写了更多测试；例如，160 个案例中有 67 个在做出实质（非桩）实现之前就有一个或多个失败的测试，而 Default 条件是 160 个中的 0 个。

就测试大类而言，TDD 每种测试都更多：既有更多小的、琐碎的测试，也有更多集成测试和端到端测试。任何「智能体在 X 上做太多或太少」的明显高层判断似乎都不成立。如果我们看具体的失败以及测试是如何漏掉它们的，可以观察到 TDD 条件下有不少这类情况。例如，Zstd 在有四个 Huffman 流时会使用一种叫跳表（jump table）的东西。

TDD 智能体更可能在这个特性的评测测试上失败，尽管它们针对一般情况写了更多测试。不知何故，TDD 智能体更可能写出不覆盖困难用例的测试（例如，让全部四个流都相同，然后还把它们的值也弄得很琐碎，正如我们在 Verus 上看到的那样）。这又是一个我会好奇 AI 实验室内部有多少可见性的案例，因为从外部看，为什么用 TDD 去「打底」会让智能体写出更差的测试和更差的实现，并不明显。

如果我们手上只有 TDD 和少数几个测试条件，一个假设可能是：TDD 的代码往往有一大堆不太好的小测试，所以用 TDD 给智能体打底会让它们写更多这类无效测试。但为什么我们在 Verus 上看到同样的模式就不清楚了。也许可以在开放模型上重跑这个实验、在某种层面上检视模型内部究竟发生了什么，从而判断这对 TDD 是否成立、以及它是否与 Verus（或其他）行为有共同原因？

有两个 skill 也促使智能体进入更迭代的方式，也许基于「执行更频繁会得到更好结果」的理论，而这两个 skill 也都表现不佳。总体而言，在所有条件下，智能体在 xhigh 和 max 上都能让它们自己写的测试通过（max 未展示，但它的正确率略高于 xhigh，成本却好得多）。让它们自己的测试更频繁地通过，反而倾向于让智能体写出更多错误测试、把错误行为固化下来。

Yossi Kreinin 对「为什么 TDD 可能导致更差的测试」有这样的想法：

> 就我个人而言，我认为如果你在写代码之前写测试，就更难测到那些更难的用例，因为你对什么会变难了解得更少；即便你做了随机测试（而我认为「TDD」并不与随机测试相关联），你也更不可能把分布引导到 bug 所在的方向。如果你写过代码、或者至少能看着代码，你就知道什么看起来显然正确、什么可能行也可能不行，因为有些东西的行为并不容易理解。换句话说，TDD 会把你引向黑盒测试，而对复杂的机制来说，在我看来黑盒测试不如白盒测试有效；我比较确定对人来说是这样，对智能体就不太确定了。

我「TDD 会表现不佳」的猜测正确吗？严格就结果而言，答案是肯定的。就我的推理而言（没有明确写下来预先登记，但我知道自己当时在想什么），我认为并不清楚。我的想法大致是：正如我们近来在[多种语境](https://danluu.com/benchpocalypse/)下[反复](https://danluu.com/ai-coding/)[讨论过的](https://danluu.com/pl-tokens/)，让智能体真正做「差不多对的事」而不只是过拟合，是智能体取得好性能或正确率的关键。就方法论整体而言（而不是这个指令如何改变了智能体行为），TDD 似乎天然容易导致过拟合。

智能体确实写了更差的测试，有时还用了相对昂贵且无效的迭代工作流；但我不确定我预想中「人类用 TDD 然后指挥智能体去实现」的那种失败模式，是不是这里真正的问题——而我的直觉正来自那种失败模式。我会给这个推理打上「也许对、也许不对」的评级；我认为需要更多评测和调查才能下结论，而且我猜额外的数据会表明我原来的推理是错的。

### Spin

Spin 是一个模型检查器。

现在我们进入了结果与平均相差不大的区间。Spin 在 medium 和 xhigh 上都比平均略差，成本低于平均。正如我们在其他形式化工具上看到的，Spin 的使用总体上是无效的。具体到这个案例，用 Spin 对某一类行为建模，与是否通过/失败覆盖该行为的隐藏测试之间没有相关性。Spin 的使用是表面化的、没有产出的。

### Hegel

Hegel 是一个基于属性的测试库，其思想来自 [Hypothesis](https://github.com/hypothesisWorks/hypothesis/)。

也许我们已经能预料到，智能体并没有有效地使用 Hegel。就它们使用它的程度而言，用得也很表面化，而且通常是在大量依赖普通测试之后才用它。由于反复说「智能体并没有真正有意义地做这件事」会显得重复，下面这些小节我会写短一点，只突出一些特别奇怪的地方。

智能体实际使用的工作流通常是：

1. 阅读 RFC 与 API/契约

2. 实现 Zstd

3. 跑普通测试

4. 阅读 Hegel 文档

5. 用 Hegel 写 1–4 个简单的基于属性的测试

6. 继续使用普通的 Rust 内置测试

如前所述，Hegel skill 并没有提升正确率。正确率反而更差（不过差距小到可能是随机波动）。更引人注目的是成本高得多（medium 高 26%、xhigh 高 41%），其原因看起来是因果性的。

这个 skill 让智能体生成更多测试。额外的测试大多是「畸形输入不会引发 panic」的检查，以及往返（round-trip）测试。前者是所有基于属性和模糊测试条件下智能体本就倾向于过度做的事，所以在那上面额外投入没有用。后者本身似乎不是坏主意（我甚至经常明确要求智能体创建往返测试，而且它们看起来确实有助于检查特定性质），但它并没有被用在最容易出错的地方。在没有额外指令的情况下，智能体倾向于对相对平凡、本来就很可能是正确的性质创建往返测试。

至于成本，原因有多个。一是这个 skill 相当大（skill 本身 3.4 万字符，还会加载一个 4.5 万字符的 Rust 专用参考，合计超过 2 万 token）。它在运行开始时被加载，并在许多后续操作中被反复读取。这导致平均额外美元成本：medium 增加 16%、xhigh 增加 18%（按原始 token 计，medium 平均增加 90 万 token、xhigh 增加 180 万 token；虽然这些内容的缓存命中率非常高——初始读取之后达到 99.85%——但被反复读取的次数足够多，仍然占了总成本的相当一部分）。

一个乘数性的成本（已包含在上述数字中）是：这个 skill 还规定了一套结构化操作，导致要做的工作多得多。这些工作没有提升正确率，因此增加了成本却没有带来相应收益。

有一点要注意：这个 skill「只」在 160 个案例中的 157 个里被使用。和用 LLM 时通常的情况一样，行为和结果是随机的。如果你手上有一个你认为智能体应该为某个任务使用的 skill，它用不用，可能取决于一些外界看来不透明的因素。

### ToB skill

这个案例中，160 次运行只有 108 次真正打开并阅读了[这个 skill](https://github.com/trailofbits/skills/blob/d3323cefbcf645678b8dc481de204b02ad3d02dc/plugins/property-based-testing/skills/property-based-testing/SKILL.md)。该 skill 建议在 Rust 中使用 proptest，但它也建议添加依赖需要审批，而这些又都是单轮自主运行，所以并没有这么做。

和目前其他属性测试案例一样，属性测试是粗糙的，也没有以有帮助的方式完成。

### Rstest

Rstest 是一个[基于 fixture 的](https://en.wikipedia.org/wiki/Test_fixture#Software)测试库。

智能体实际上没有使用 rstest。它们技术上确实用了，但基本上只是在 rstest 里写标准单元测试，没有按 rstest 的预期方式使用它，从而丧失了 rstest 的意义。虽然从高层看，这一点对目前见过的技术或许都成立，但智能体至少表面上用了其他技术的一些用法（比如用 Hegel 写一些低价值的属性测试）；而在这里，智能体完全没有用到「让 Rstest 之所以是 Rstest」的那个东西（类比到基于属性的测试库，那就相当于它们只是用这些库写了非属性的单元测试）。

### Rust test

这里指的是智能体在 Default 条件下使用、也在其他条件中大量依赖的标准 Rust 内置测试框架。

显式要求智能体使用内置测试框架，确实带来了更多测试（medium 翻倍、xhigh 增加 25%），但这并没有带来更好的正确率。智能体出错时，往往是因为没有测试重要行为，或者实现了错误的测试行为。增加更多测试，并没有实质性地提升对高风险行为的覆盖，也没有降低「测试里编码了错误行为」的运行占比。

Yossi Kreinin 补充道：

> 我认为固定输入/输出风格的测试，在机器和人身上都助长了这种情况。如果你生成输入，你就得接着有代码来判断输出正确与否；这段代码本身可能有 bug，但它至少让你比「跑一下代码、就假定它的输出是正确答案」更容易去思考「正确」意味着什么、以及如何判断是否正确。有了固定输出，你很可能会直接把代码的输出编码下来，然后说服自己它讲得通。

### Creusot

Creusot 和 Verus 处在同一领域。

正如我们在其他形式化条件上看到的，Creusot 没有被有效使用。

### 变异测试

[变异测试](https://en.wikipedia.org/wiki/Mutation_testing)通过修改代码来判断测试有多有效，然后添加测试以获得好的覆盖。虽然「变异测试」是一个标准的编程术语，但智能体通常并没有真正做变异测试，而是做普通测试，外加一点点以并不真正算变异测试的方式对东西做变异——类似于 TDD 指令改变了行为但没让智能体真正做 TDD。

有少数案例确实发生了变异测试，但量很小，而且很少见。

### Judgement

这个条件要求智能体根据自己的判断，适当地自适应使用测试方法。鉴于我们目前看到的，毫不意外，智能体大多使用了标准 Rust 单元测试。少数智能体做了一点有限的模糊测试。智能体可以使用其他测试和形式化库，但它们并没有用。

### 模糊测试

模糊测试以某种方式随机化测试输入。

智能体严重依赖发送随机字节，这大多导致走向相同的代码路径（无效输入）。智能体也尝试发送有效输入的随机变体，这大多也只是反复锻炼输入拒绝路径。

在少数生成随机结构化输入的情况下（160 个案例中 10 个），这有一半的时候找到了真正的 bug，其中一些还不是平凡案例。160 个案例中只有 5 个稍微有效地用了模糊测试，这算不上好，但这是我们目前见过的技术中比较有效的用法之一。这也似乎说明：智能体可以被训练得在这上面做得更好，也可以在不改变训练的情况下被引导做得更好。从某种意义上说，它们确实知道怎么做；只是通常不会在没有被推着走的情况下去做。

### Insta

Insta 是一个快照测试（有时也叫金标准测试）库，它把结果与一份「快照」或「金标准文件」中记录的正确结果做比较。一般说来，快照通常是某种序列化数据，比如某个数据结构的 JSON 对象、CLI 输出日志等等。

如你所料，快照测试几乎没被使用，智能体大多依赖传统测试。智能体确实用了 Insta，但常常只是把普通单元测试写进 Insta 里。

### SMT

智能体被要求使用 [SMT 求解器](https://en.wikipedia.org/wiki/Satisfiability_modulo_theories)，环境里装有 Z3、cvc5 和 Yices。

智能体大多把 SMT 求解器当作一种草稿本来计算 FSE 状态范围、头部算术之类的东西。即便智能体对某些东西建模，它们通常也没有对正确的东西建模，从而避开一个常见错误。

例如，有一个计算本该是 `byte1 + (byte2 << 8) + 0x7F00`。许多智能体实现成了 `byte1 + (byte2 << 8) | 0x7F00`。智能体用 SMT 求解器证明了与这个计算相关的性质，但之后仍然写错了代码，使得 SMT 的使用看起来并不比 Default（不加指令）更好。

### TLA+

TLA+ 是一门用于建模行为的语言和工具。

我们进入了高于平均的结果区间（但仍比 Default 差），不过如前所述，我不会太当真对待实际排序。虽然这未必显著，但 TLA+ 在 medium 上得分略高于平均，在 xhigh 上高出更多。

160 个智能体中有 159 个创建了某种 TLA+ 模型，通常是 Zstd 的状态机模型。具体到覆盖范围，有 30 个建模了 Huffman/FSE/熵（经常出 bug 的区域）。和其他形式化案例一样，TLA+ 建模发生在流程中相对较晚的阶段（在大量标准测试和实现之后）。智能体有时会发现并修复 TLA+ 模型中的错误，但我没有发现任何一个案例中 TLA+ 的问题导致了 Rust 代码的实际改动。

虽然确实发生了一些看起来像模像样的 TLA+ 建模，但如果说它提升了正确率，那也是以一种很难观察到的小幅方式。总体而言，TLA+ 建模更精细的运行，正确率并没有更好。

### 蜕变测试

在蜕变测试中，我们检查相关的输入是否产生具有预期关系的输出。例如，可以检查对于一个排序函数，改变不相等输入的顺序不会改变输出的顺序；或者对于加法，给某个输入加上一个值会（在模溢出意义下）给输出加上该值。

正如我们在其他条件上看到的，蜕变测试在正确率方面没有被很有用地完成。确实检查了一些其实挺合理的性质（例如，在帧边界插入一个可跳过的帧不应改变输出；合法的块重划分不应改变输出等等），但这些性质并没有命中智能体相对频繁出错的区域，所以检查它们没有帮助。总体而言，智能体似乎是这个老笑话的粉丝：

> 一名警察看到有个醉汉在路灯下找东西，就问他丢了什么。醉汉说丢了钥匙，于是两人一起在路灯下找。几分钟后警察问他是否确定是在这里丢的，醉汉回答不是，是在公园里丢的。警察问那为什么在这里找，醉汉回答：「因为这里有光。」

奇怪的是，蜕变测试在 xhigh 上用得比 medium 还少。

### ECC

[ECC Rust 测试 skill](https://github.com/affaan-m/ECC/blob/e04ea0b9cc8248686edf5ac751cadff550e162b8/skills/rust-testing/SKILL.md) 表现还行，但主要因为 skill 的很大一部分被忽略了。智能体通常会打开并阅读这个 skill（160 个中有 153 个读了），而这似乎让它们生成了更多测试。不仅这个条件下智能体生成了更多测试，而且如果我们看智能体何时阅读该 skill（早读 vs. 晚读 vs. 从不读），会发现测试增加量上存在一个基于暴露程度的梯度。

虽然 ECC 的得分几乎和 Default 一样好，但根据智能体在更多暴露于该 skill 时的表现，我猜这是随机的。智能体越早看这个 skill，其行为受影响越大，正确率结果也越差。

ECC 在原始分数上看起来还行，是因为那 7 个没读 skill 的智能体表现异常好、拿到了 100% 正确率，而那 9 个很晚才看 ECC、只受到极轻微影响的智能体也表现很好、拿到了 100% 正确率。这也解释了 ECC 那个不寻常的结果——medium 和 xhigh 得分相同（在那些智能体实际上没怎么读 skill 的运行里，除了一次之外全都发生在 medium）。虽然智能体何时被调用 skill、何时没有，可能存在某种偏差，但整体模式表明：**除非你认为 ECC 像护身符一样能带来好运，但只在 skill 真正没被使用时才起作用**（而这种情况在更低 effort 下更可能发生），否则 ECC 并不有效。

当然，智能体不应受一个它们没看过的 skill 影响，我们应该基于 skill 被使用的那些案例来打分。如果看 skill 真正影响了智能体的案例，ECC 得分低于平均（介于 Rust 内置框架和 Creusot 之间），失败模式与 Rust 内置框架非常相似——有大量小而没意义的测试。该 skill 让智能体使用红-绿 TDD。智能体的行为大概不是 TDD 实践者会称之为 TDD 的那种，但智能体确实会在实现功能之前写一个小测试，这导致测试数量庞大。如前所述，这对智能体来说不是一种有效的开发方式，所以结果比不加指令、也不加 skill 更差。

顺便一提，[正如我们在尝试 Caveman 模式时指出的](https://danluu.com/ai-coding/#caveman-mode)，方差相当大，人们常常被几次小规模运行误导、以为某个 skill 有用。这次我们对一个 skill 试了 160 次运行——相当多的数量，比任何理智的人会做的都多。然而表面上，只看分数的话，ECC 似乎还行。

我们需要多得多的运行次数，才能把使用 LLM 时固有的噪声平均掉。我们可以像这里所做的那样去做，[检视结果、动动我们的人类大脑](https://danluu.com/brain-off/)；但在人们谈论公开的 LLM 基准时，我很少看到有人这么做——无论是针对 skill 还是别的什么（我确实试过让 LLM 去分析结果，但一如既往，即便用当前公开的 SOTA 模型，分析也很差、充满基本的推理错误）。相反，我大多看到人们传播那个头号数字，即便它出于无聊的统计原因并不有意义，或者更糟——[基准本身存在致命缺陷，就像我们在 Senior SWE-Bench 上看到的那样](https://danluu.com/exercise-7/)。

### Default

Default 不给智能体任何测试或验证指令。

鉴于我们目前看到的，Default 得分高于平均并不令人意外。当被要求使用特定库或特定测试技术时，智能体通常做的事情都没有用。由此可以推出：**不告诉智能体去做那些会让它们做无用功的事，比告诉它们去做那些会让它们做无用功的事要好**。

### Audit

Audit 要求智能体在实现之后审计代码。160 个智能体中有 152 个真的做了这件事，其中 151 个声称发现了问题并因此做了修改。智能体一般会挑选出合理的审计区域，但通常不会用全新的上下文做独立审计（我经常要求智能体这么做），而且常常在审计中重犯它们已经犯过的同一个错误。

有 42 个使用了独立 agent，但这些运行实际上得分更差（有可能并非因果——智能体可能是因为处境更糟或更难，才决定派生一个独立审计）。Audit 最终在 xhigh 上取得了最好的正确率，但在 medium 上低于平均；而所有这些审计都大幅增加了成本，尤其是在 xhigh 上。平均而言，Audit 的表现和 Default 差不多，而它在 xhigh 上是否真的更好、在 medium 上是否真的更差，并不清楚。这是可能的，但我认为我们没有足够证据来判断。

Em Chu 有如下评论：

> 这里的结果与我的经验一致。审计代码是目前我花掉最多 token 的地方，因为我觉得它相当有用。不过我总会给两条指令：不要派生 subagent。你自己去读、去理解代码/diff。不要执行任何代码。因为我发现，如果你让 LLM 做这两件事中的任何一件，它都会明显变笨（当然，我没测过……）。它默认真的不会去读或推理代码，即便我从没做过大到超出它上下文窗口的修改。我通常还会加一些废话，比如「要有对抗性」「考虑特性的所有可能组合」「考虑整个输入空间」，但我不太确定那到底有没有用。

试试那个会很有意思，但正如我在最近几篇帖子中指出的，我在尝试让帖子写得不那么细，所以也许那会是另一篇文章的主题。

### 审计并模糊测试高风险区域

对 Zstd 而言，当这条指令被遵循时，它会让智能体重点聚焦于 [FSE](https://github.com/cyan4973/finitestateentropy)、[Huffman](https://en.wikipedia.org/wiki/Huffman_coding)、比特读取器和状态。这些区域一般来说是智能体经常漏掉问题的区域，所以智能体认为这些区域有风险是对的。被瞄准做模糊测试的区域比单纯的 Fuzzing 条件选得更好。

在 medium effort 下，智能体大多忽略了这条指令、没有做；但在 xhigh 上它们确实遵循了指令。虽然这个条件表现不差，但似乎也没有比不加指令更好。

看智能体实际做了什么，一个问题是它们常常只是生成一堆随机输入，而这些输入大多是无效的、测不到任何有意思的条件。

当人类测试者生成随机测试时，他们通常会设法把随机性引导到能生成「有意思」输入的方向上，而智能体没能做到这一点。智能体也没有很有效地检查输出，很多情况下只检查是否崩溃。模糊测试常与「只检查崩溃、不检查性质」联系在一起，所以这也许不太令人意外，但如果有人在测试一个 Zstd 实现，这大概不是他们想要的。

### 不要犯错

虽然这个条件在技术上得分高于 Default，但行为似乎没有实质区别，分数也相当接近；我猜这是随机波动造成的。在我检视结果的每一个层级上，它都与从 Default 中随机抽取的样本无法区分。

### Kani

Kani 是一个 Rust 的[模型检查](https://en.wikipedia.org/wiki/Model_checking)库。

就「真正把形式化方法用在将要执行的代码上」而言，Kani 的覆盖最好——Kani 确实被用在了 Zstd 代码上。然而，这只在偶尔发生，大多数使用都是表面化的。

有一个案例中，真实的 Kani 使用抓到了一个非平凡的 bug，导致 Rust 代码被修改。160 次里 1 次算不上惊人，但它确实说明智能体有时能摸索着合理地使用 Kani（我猜这意味着，如果在 RL 环境里使用，模型可以学会更有效地使用 Kani）。

Kani 的成本明显高于其他条件。这似乎是因为反复读取 Kani 输出很昂贵，导致很高的输入 token 成本。

### ACL2

ACL2 是一个定理证明器。这里结果要注意的一点是，很多情况下 ACL2 会 OOM（192 GiB 上限）。OOM 的结果没有被计入，这以某种不透明的方式使结果产生了偏差。

虽然 ACL2 得分高于 Default，但如果认为这是因果且显著的，我会感到意外。正如我们几乎在所有其他形式化方法上看到的，ACL2 大多被用来证明一些对正确率没有显著影响的东西，所以不清楚它为什么会提升正确率。

在这么多不同的条件里，除非其他条件都严重退化，否则我们不会指望 Default 或表面上等价的「不要犯错」排在最前面。

### Proptest

Proptest 是一个基于属性的测试库。

正如我们在其他随机化测试上看到的，大多数测试不太有意思，而对随机性的过度依赖导致覆盖很差。

尽管对基于属性的测试使用普遍很差，proptest 的收缩（shrinking，即找到导致测试失败的更简单输入）有时确实提供了价值，这比我们在大多数其他案例中看到的「几乎没有价值」要好。

### 基于属性的测试

和其他基于技术的方案一样，智能体有一个装好所有选项的容器。每个智能体都选择使用 proptest，所以这实际上变成了第二个 proptest 条件。

和 proptest 条件一样，测试大多不太好，但它们有时确实找到了 bug，收缩似乎也带来了一些收益。

我觉得有点意思的是，这个第二个「意外」的 proptest 分支也同样高于平均，和 proptest 一样。

### Skill

这里的 Skill 是指我自己写的那个 skill，用来测试「拥有一个简单 skill」的效果（相对于我让 agent 去找相关测试 skill 时找到的那些大而复杂的 skill）。

也许我应该用 skill，但我一般不用，而是依赖提示词、看结果、再继续提示。因此，我对什么构成一个好 skill 没有任何直觉，因为我没有练过；不过 Max Bittker 建议说，用一个测试 skill 来尝试把我脑子里关于测试的一些信息编码进去，看看结果会很有意思。看到这个结果后，他的反应是「我早就跟你说过」。

我没有为这个预先登记猜测，但我脑子里的猜测是它不会很有效。[从我 2015 年试图向人类传达这件事的尝试](https://danluu.com/testing/)来看——我会说那次基本上失败了——我认为自己并不擅长用文字明确说明一个人应该如何测试。我曾坐下来给人演示该怎么做，这通常能让他们终身受用、把他们变成[远超平均](https://danluu.com/p95-skill/)的 bug 发现者；但[通过演示向某人传达一件事，与通过写下做法来传达，是两种不同（且后者更难）的技能](https://danluu.com/hardware-unforgiving/)。

在这个案例中，skill 内容是：

- 在实现之前，思考哪些区域可能有细微 bug；对每个区域，说明可能的错误和看似合理的替代解释，然后设计一个在结果上会体现差异的检查（优先在边界两侧使用非对称/边界示例）

- 实现之后，对高风险区域，在不接触生产代码上下文的情况下独立重新推导结果并比较（全新上下文，不要复用辅助函数）

- 在可行时，使用基于属性的测试或随机输入来探索空间，尽量减少在「不 panic / 不崩溃」这类随机化上的投入

- 随机化时，倾向于选择能探索有趣状态和代码路径的输入（不要只是天真地随机化那些都会落入同一错误路径的输入）；这可能需要结构化的随机输入

- 如果对细节不确定，用独立推理来检查什么才是正确的（全新上下文，不要复用辅助函数）

这拿到了最高分，但并没有按预期奏效。它几乎从未真正做「全新上下文」这件事，所以把这条放进去毫无意义；我们也不知道它究竟是一种有效的、需要被改进以强制智能体更频繁执行的做法，还是一种应该被移除的做法（虽然理论上它可能正以最优频率发生，但我非常怀疑）。

我们在「审计并模糊测试高风险区域」中提到，智能体似乎知道如何识别高风险区域。这里也是如此，但这未必意味着智能体做了对的事。例如，智能体把 Zstd 中编码与解码之间比特流被反转识别为高风险，但在锻炼这一点的测试上并没有做得更好。如果看具体例子，在 medium 的第 35 次运行中，一个智能体把这一点识别为高风险，做了独立推导和一次审计，但仍然失败了。它有一个相关的测试，但输入是回文的，所以反转顺序得到相同结果，从而让一个把顺序弄反的错误实现得以蒙混过关。

另一个问题（如果我们能称之为问题的话）是，所有的模糊测试/基于属性的测试都是「手工」做的。既然智能体似乎挺会用 proptest，而 proptest 又有一些可依赖的有用机制，这个 skill 大概可以通过指示智能体使用 proptest 而轻易改进。那些旨在尽量减少「生成大量无用的、过于随机的测试」这一标准失败模式的指令，方向上起作用了，更大比例的智能体生成了多少有点意义的测试，但这些测试仍然比我期望一个人类（或一个有人类积极指导的智能体）写出的要差。在不再迭代的情况下，我不确定什么样的通用指导会是好的（相比之下，花几分钟看看 Zstd 的结构、给出针对 Zstd 的具体指导，是我在其他问题上用得很有效的一类做法）。

作为一份供迭代的初稿，我不觉得它糟得可怕，但我也不觉得它真能用了。如果能用更多示例去验证、以确保没有对类 RFC 问题、位操作密集问题等过拟合，我看到一个改进版可能行得通；但由于我通常不做 skill、也从未尝试迭代过 skill，它没能捕捉到我或其他人在真正驱动一个智能体时会做的事。

由于我习惯于「提示→看结果（不一定是代码，但至少是智能体说自己做了什么、以及某种关于发生了什么的智能体式总结；对某些实验性工作则会看部分实际结果）→基于此再提示」，我不习惯前置信息，而前置信息与响应信息是相当不同的问题。从以前的模糊测试工作中，我见过智能体常犯的失败模式，这个 skill 本意是防止这些失败模式；但如果你至少偶尔回来检查一下，这比完全前置要容易做到，而且前置指令不足以阻止标准失败模式，尽管它们确实有所缓解。

### 总体评论

如我们上面提到的，我没有以漂亮、易看的方式拆解数据。之所以没有，是因为一旦我们看智能体实际做了什么，它们看起来大多相当无效，而我觉得看「糟糕使用 Verus 的智能体」比「糟糕使用 QuickCheck 的智能体」好多少，并不是特别有意思。我觉得有点意思的一点是：当被要求识别有风险或容易出细微 bug 的区域时，智能体能够做到这一点。

但总体而言，无论建议的是哪个库或技术，智能体都没能真正使用该技术。[正如此前讨论的](https://danluu.com/ai-coding/)，仅仅要求智能体「测试」、或反复要求它们多测试，结果都是糟糕的测试。事实证明，要求它们使用测试技术（其中一些我个人觉得非常有效），同样会导致糟糕的测试。我快速草草写的那个 skill 似乎能稍微改善情况，但需要的不只是我花的那 2 分钟才能真正有用。Yossi Kreinin 评论说，软件测试的现状很糟糕，因此如果智能体退回到它们的训练（可以这么说），我们就该预料到糟糕的结果——而这正是我们看到的。

不知何故，智能体似乎在使用 proptest 上稍微好一些，尽管其测试水平远低于我期望一个读过 proptest 手册、又得到一些测试方向的合理人类所能达到的。我很好奇，得到更多指导的智能体在使用 proptest 上是否会比其他库更有效——但那是另一篇文章的主题了，因为我一直想让帖子在半小时内写完，而这里已经接近 9000 词，超出了半小时内合理打字量的范畴。

### 如何让智能体写出好测试？

我的经验是：如果你引导智能体搭建一套合理的测试与分诊（triage）结构，那么让智能体在此基础上有效添加内容、而不需要大量监督，效果还凑合。由于我的背景（偏见），我倾向于依赖的测试是某种随机化测试 / 模糊测试 / 基于属性的测试。

我和 Jamie Brandon 聊过这个，他在快照测试上发现了同样的情况。他提到，在某个项目上，他要求智能体（用多种模型）做快照测试时，它们会说自己在做，但实际并不做（它们会写一个单元测试，然后说它们写了一个快照测试）。在另一个项目上，他设法让智能体写出了合理的、mock 了 IO 的端到端测试，但前提是把测试移到单独的 crate 里，并在 AGENTS.md 中写明「测试要留在该 crate 内、不要修改公共接口」。

至少到目前为止，我在「让智能体写测试代码」这件事上比 Jamie 依赖得更重（我倾向于在 CLI 里给智能体打字；至少目前，他比我更偏好手写大量代码），但只要你搭起某种合理的结构，怎么做似乎并不重要。

[与我们此前看过的某个问题类似](https://danluu.com/ai-coding/)，似乎只要做任何勉强合理的事都能起作用。如果你「跟」智能体说话、给它一些轻量指令（就像我们在 Zstd 或 IMAP 评测里做的那样），它会做得糟。但如果你看看它做了什么、再多打几句话，你往往能很快把它带到一个不错的状态（至少这是我在其他问题上的经验）。我从未尝试理解是什么让模型奏效，所以我编造的、很可能完全错误的猜测是：模型内部某处对如何做这些事有某种理解。它不是默认行为，甚至没有接近默认到「只要说出用哪个技术」就能奏效的程度；但如果模型被充分「打底」，做这些事的知识就会真正被付诸实践。

我很好奇，这是否能被有效地打包进 skill，或者 AI 实验室是否会开始训练模型、让它们在测试或形式化方法上变得更好，又或者它们正在做的那些不直接改进这些能力的事，是否会间接改进到足以让智能体在无需太多监督或结构的情况下写出像样的测试。

### 预测准确度

- **TDD 会表现不佳**（55% 信心）→ 真
- **形式化方法不会超常发挥**（52% 信心）→ 真，但原因和我预想的不同。智能体根本没能有效地使用它们，所以它们当然无法超常发挥
- **「不要犯错」不会胜过「不加指令」**（95% 信心）→ 真；它胜过大多数条件，是因为「什么都不做」比「让智能体做无效的事」要好
- **ECC skill 不会超常发挥** → 真；如果我用 skill 更多，我会对此更有信心，因为该 skill 的文本大多似乎什么都不会做，而那些看起来会做点什么的文本，看起来是有反效果的
- **Hegel skill 不会超常发挥** → 真；又一个「如果我用 skill 更多就会更有信心」的案例，因为它没奏效的原因恰恰是我猜到的；我只是对自己的感觉毫无信心
- **ToB skill 不会超常发挥** → 真
- **Lean 在形式化方法中会表现较好** → 假
- **我的 skill 会表现平庸到糟糕** → 假，尽管 Max Bittker 正确地猜到了会发生什么、提前告诉了我，并给出了一个与后来实际发生情况一致的原因；当别人说出了某件事将要发生的原因而你不相信，然后它偏偏就因为那个被点名的原因发生了，这让人觉得自己很蠢

### 关于 skills

在不同时期，我曾觉得自己有一套糟糕/过时/无效的工作流，因为我听到人们在做什么，而我又太懒没去尝试。我对 skill 有这种感觉已经有一阵子了，因为我并不怎么用 skill。相反，我维护着一个很大的草稿本，里面放着一些我有时会复制粘贴进去当提示词的东西——这感觉有点像用「把代码块注释掉来保存」代替版本控制。

但后来[我看了 Thorsten Ball 的这个演讲](https://thorstenball.com/talks/how-i-prompt/)，他提到自己并不重度依赖 skill；我又和一些似乎相对高效使用 LLM 的人聊过，他们也不太用 skill，这让我怀疑自己是不是没损失什么。

然后我做了这个实验。我的感觉是，我看过的那些 skill 不会有帮助，而且很可能实际上有害——不过信心很低，因为我对 skill 一无所知。这些 skill 基本按我想的那样表现，所以我从「看智能体如何响应、跑一堆小实验」中获得的直觉，在 skill 上似乎还挺站得住脚。我还看过一些其他据称能提升测试的 skill（没有纳入本次实验），它们看起来会有和本次测试的 skill 相同的失败模式。

我还跑了两个实验（细节这里不讨论，也许以后写一篇 1 万字的文章再说），测试一些公司为支持自家产品而提供的「官方」skill。一个来自一家大型 AI 实验室，另一个来自一家「小」的、几十亿美元的公司；但在两个案例中，这些 skill 都让结果变差了，就像我们这里看到的一样。有趣的是，做完这些实验后，我实际上对**个人使用**的 skill 比以前更看好了，因为失败模式似乎是可以预测的，因而无需花费大量昂贵的实验就能修复。创建一个公开发布的、旨在真正好用、能跨不同模型和 harness 良好工作的 skill，似乎可能很难（Claude 和 codex 似乎「想要」不同风格的提示词，所以对 skill 自然也该如此），但仅仅解决那些导致许多 skill 对个人使用而言还不如没有 skill 的问题，似乎相当可行？

### 关于 skill 写作的朴素想法

我对 skill 的了解还不足以说出怎么写一个好 skill；但在本文看过的所有 skill（除了我花一两分钟写的那个）以及另外两个实验里的 skill 中，这些 skill 看起来都像是**以人类教程指令的方式写的**，即 skill 的目标似乎是解释如何做某件事。作为一个只写过一个 skill 的人，我的朴素想法是：当面对的是一个本就对主题有一定了解的模型时（本文和另外那些实验里都是如此），这大概不是最优的做法。模型已经有某种默认行为分布，所以我觉得更自然的做法是给出**能修正该分布**的陈述，而不是写出那种足以让一个人类或一个毫无知识的智能体从零学会该行为的指令。

一个明显的问题是，不同的 harness、模型和 effort 会给我们不同的默认行为，而把一大堆文本塞进提示词或 skill 并不会改变这一点；那只是用更长的篇幅把智能体推离默认，其中还夹杂着大量可能会产生某种非预期推动的文本。正如我们这里看到的，很多文本直接被忽略了（至于哪些被忽略、什么时候被忽略，当然取决于 harness、模型和 effort）。例如，对于 ECC skill，即便它被阅读了，其中大部分指令也被忽略；虽然 TDD 指令有影响力（这让结果更差），但那些要求做 TDD 的指令其实并没有被真正遵循，尽管它们被清楚地写了出来。

由于有效的提示方式会随模型版本和 effort 改变得足够多，对于「好好测试代码」这样通用的东西，我不清楚这些 skill 如何在如此多的模型和 effort 之间起作用。仅仅从 GPT-5.5 到 GPT-5.6，我的工作方式就发生了实质变化，因为很多在 GPT-5.5 上相当可靠的做法要么失效了、要么变得不可靠得多（尽管整体能力水平看起来更高了）。就像我不会用提示 GPT-5.5 的方式去提示 GPT-5.6 一样，我大概也不想使用同一套 skill。

我不确定除了 AI 实验室里的人之外，还会有谁愿意费这个劲去对 skill 跑评测、看看对每个模型和 effort 什么有效，然后创建一个按模型和 effort 区分的 skill 组合；我也不指望 AI 实验室会拥有针对竞争对手 harness 和模型优化的 skill。所以对于通用的「测试」skill 我不太看好（如上所述，我看过但没在这里测试的不少测试 skill，看起来会有和这里测试的既有 skill 完全相同的失败模式）；但我能想象拥有少数几个适用于我自己用例、针对我常用的特定 harness/模型/effort 的 skill。

仅就测试而言，虽然某些模型在某些 effort 下会掉进特定陷阱、我想把它们推离这些陷阱，但我并不真正想要一个独立于被测对象、独立于我想要的质量水平和质量维度、面向智能体的通用测试工作流。所以我想我不会想要一个通用的测试 skill，去规定一套智能体一般应该执行的测试步骤。这类情况适用于我做的很多任务——我希望它们以任务特定的方式完成，而不是通用方式。我能想象某种 skill：它先问我一些问题，然后向智能体输出正确的指令；但鉴于模型进步如此之快，如果我是为个人使用而做东西，我认为花时间调这样一个 skill 直到它有用并不划算。如果我是在做一个智能体产品、想让更多人使用它，那可能是另一回事；但我试过的 skill 都有和本文测试的 skill 相同的失败模式，所以做一个最终并不会多有效的 skill，似乎相当容易。

我能看到 skill 在诸如「教智能体执行工作流」或「如何与 API/界面交互」这类事情上可能普遍有用，比如 [Sawyer Hood 那个帮助智能体驱动浏览器的 skill](https://github.com/SawyerHood/dev-browser)。由于我没试过那个 skill，我并不是在背书它；但读过之后，它看起来是那种能很好工作、并在我试图让智能体驱动浏览器时省去很多麻烦的东西。然而，如果你读一读实际的 skill（和脚本），它的风格与本文测试的那些测试 skill 非常不同。

### 附录：智能体的蠢事

在让一个智能体为某项分析做一次简单查找后，它执行了一个 perl 进程，跑了 2 小时 20 分钟，直到我把它杀掉（我真的需要一个能自动抓住这类事情的东西，因为这种情况相当常见）。

一个 subagent 用 perl 对一个相对较小的文件（44kB、1364 行）做正则搜索，但这个表达式在 PCRE 下是退化的，做了组合量级的工作。我用[我们在这里花几分钟尝试构建的 FRE 正则引擎](https://danluu.com/benchpocalypse/)重跑了一遍，0.7 秒就完成了匹配（Rust regex 是 0.6 秒）。

你永远不知道智能体在外面做事时会出什么状况，但至少这里是有办法预防的。第一，智能体本可以避免调用一个会产生这种组合爆炸的正则引擎；似乎没有强有力的理由不在这上面使用更安全的正则引擎（比如默认设置下的 ripgrep）。第二，智能体本可以检查它试图发出的正则；它实际发出的正则返回一个无用的大捕获组，而且成功时并不能做到它想做

的事。第三，subagent（或 harness）本可以在 subagent 结束后自动杀掉这类进程。当然，这不应该适用于 subagent 运行的每一样东西，但智能体经常留下这类失控进程（在这个案例里，看起来启动它的 subagent 在 30 秒后就停止了，却把这个进程无限期地留了下来——尽管这样一次搜索本应返回一个供该 subagent 使用的结果，而 subagent 一旦结束，这个结果就没有价值了）。

我实际上有一个进程，会四处清理智能体留下的东西（会泄漏内存的智能体、占用空间的临时构建产物等等），但它没有在找失控的 perl 进程。这是又一个要加进去的项；但肯定不止我一个人遇到过这个问题。我猜我可以把自己这个傻乎乎的工具开源出来，但一旦主要 harness 修好这类问题，它就应该会过时，所以如果我开源它，别人也根本没什么理由去接手，因为 AI 实验室大概用不了多久就会修好这类问题。

### 附录：实验细节

为了写快点，这部分我就不写了（抱歉！）。各条件之间的分布[与我们在考察语言如何影响正确性和 token 成本时看到的并无本质不同](https://danluu.com/pl-tokens/)。不知怎的，这篇我本想半小时快速写完的文章已经接近 1 万词——这绝对超过半小时的写作量（半小时 1 万词相当于每分钟 300 多词）。

我要指出一点：[就像这篇关于编程语言的文章一样](https://danluu.com/pl-tokens/)，有一些结果看起来非常有意思/有说服力（至少从只看顶层图、看有没有什么突出的东西的角度看是这样），但更仔细看时，它们是由一个实验错误造成的——错误来自给智能体一个简短提示去搭建实验。修正这些错误后，我们得到了一个无聊得多的负面结果，除了「codex 建议可能有用的那个 skill 似乎起了反作用」这一部分。

1. 总的来说，我认为 IMAP 的结果没那么有意思。我本来以为它可能更有意思，因为它更像一个「业务逻辑」问题，而且不像[我们考察语言时看的 pandoc 评测](https://danluu.com/pl-tokens/#pandoc)那样又大又贵——后者对某些效果较差的语言，每次运行要花超过 1000 美元的 API 成本；而在 Rust 上跑到只有 30% 测试通过，每次运行也还要 700 美元（注意这个评测用的是更难的指标，即取得满分的运行占比）。在 IMAP 评测中，只有一次运行取得了满分（「不要犯错」，medium 档）。总体而言，有些逻辑片段显然对 5.6 Sol 来说太难、无法一次性搞定。一种看法是：「不要犯错」以 medium 档 2.5% 的得分碾压了其他所有条件的 0%。终于，有证据表明「不要犯错」有效了！如果我们看实际结果，和之前一样，所有方法都不太有效——即便是那些你可能觉得会很契合的方法。例如，你可能会认为 TLA+ 会表现不错，因为它天然适合 IMAP 的状态与并发；原则上，它应该很擅长对协议中很多高层部分建模。然而，正如我们在 Zstd 结果中看到的，智能体「决定」先用 Rust 做完大部分实现，然后才掏出初始提示词里要它们用的那个工具（80 个智能体中只有 5 个在编码之前真正用了 TLA+，而 75/80 是反过来的顺序）。不知何故，智能体几乎总是决定用 TLA+ 来建模一个小的邮箱变更。没有一个智能体用 TLA+ 去建模多个观察者、事件队列、UIDVALIDITY 和邮箱纪元（mailbox epochs）之类的东西——而这些正是智能体在实现中犯了很多错误的地方。相反，智能体建模的是 CONDSTORE 和 QRESYNC 之类的东西，而在这些方面 Default 条件的测试通过率超过 99.6%，TLA+ 智能体尽管建模了这些东西，通过率反而更低。我为这个主题尝试的所有评测有一个共同点：它们都是 RFC，而 RFC 极不现实——但不现实的方式是，它们的规格比几乎所有程序员让智能体实现某物时给出的规格都更清晰、更详细、更少歧义。我预计我们在这里看到的失败模式，在大多数真实问题上会相同甚至更糟。 [↩](#fnref:I)

2. 有意思的是，当我让 ChatGPT 对这段进行事实核查时，它告诉我这一段是错的，因为有论文表明人们已经用 RL 环境来训练智能体做测试，然后它链接了三篇论文——这些论文训练智能体像大多数程序员那样写单元测试，从而训练它们写差测试。那恰恰就是我会预期导致我们今天看到的 LLM 差测试的那种做法：需要有一个懂更有效测试技术的人来引导智能体。在多个关心正确性的独立子领域中，人们各自独立地收敛到了几组相关的技术上，而这些技术通常与「写小单元测试」相反。当然，训练智能体去做这种与「人们认真对待正确性时所做的事」相反的事情，不太可能带来好的正确性。确实有一些与 RL 环境和随机化测试相关的工作，[比如这篇论文](https://arxiv.org/html/2509.20384v1)，但基于模型在没有具体指导时对 {PBT、模糊测试、随机化测试等} 中的任何一项有多无效来看，这似乎并没有以严肃的方式进入大型 AI 实验室的模型训练。 [↩](#fnref:U)

3. 也许人们为「语言优越性」给出的理由是等到模型大幅变强之后才会成真，但似乎没有任何理由认为事情会那样发展。如果非要我猜，我会猜它更像扑克：人们对什么最有效有各种各样的想法，而一旦模拟变得足够强大、计算机能在很多情况下击败人类，这些想法就被推翻了。即便是像「范围优势（range advantage）」这样的「现代」概念——人们常说它与最优求解器打法一致——[一旦细看，实际上根本推不出求解器数据](https://www.reddit.com/r/pokertheory/comments/1q8gegw/range_advantage_is_a_myth/)。它们只是[好听的鸡尾酒会概念](https://danluu.com/cocktail-ideas/)，容易理解、听起来有说服力。如果我们谈的是人类学习如何与人类打扑克，那这类概念也许仍有意义，因为休闲玩家一般不会愿意研究求解器路线到足以理解什么是接近最优的程度；但如果我们谈的是编码智能体擅长什么、不擅长什么，我看不出有什么理由在我们能跑实验看什么有效时还去抛这些鸡尾酒会概念——而且迄今为止跑过的实验，并不支持那些关于「X 为什么好或坏」的抽象理由中的大多数。
