# 超越炒作：GitHub Copilot 的效率—吞吐量缺口

> [cacm.acm.org](https://cacm.acm.org/research/beyond-the-hype-the-efficiency-throughput-gap-with-github-copilot/)｜分类：Research / 研究
> 副标题：一项真实世界现场研究考察 GitHub Copilot 在企业环境中如何影响工程生产力。
> 作者：Fei Liu、Todd McKinnon（Okta, Inc.）
> 发布：2026-09-17（《Communications of the ACM》2026 年 10 月号，第 69 卷第 10 期，第 68–77 页）
> DOI：https://doi.org/10.1145/3797488｜许可：CC BY 4.0

AI 辅助工具在软件开发中的迅速普及，重新点燃了人们对工程生产力的兴趣。然而，要整体理解这些工具对工程生产力的真实影响，仍困在两种叙事之间：一边是营销宣称的显著收益 [1], [2], [22]，另一边是聚焦任务级改进的早期研究 [5], [8], [10], [20], [23]。尽管营销叙事正被不断涌现的真实世界证据所挑战 [11]，社区仍缺乏深入的、非轶事性的研究——不仅能观察到、还能解释这种脱节。本文正是要做这件事。我们提出并研究**效率—吞吐量缺口**（efficiency-throughput gap）：一种个体开发者效率提升未能转化为可衡量的组织吞吐量的现象。基于**组织欧姆定律**（Organizational Ohm's Law, OOL）框架，我们的真实世界现场研究提供了一套方法，既能实证记录这一缺口，也能给出数据驱动的解释。

**研究动机与原则。** 这项工作的动机，是理解 GitHub Copilot 对工程生产力的影响，从而为生成式 AI 与现有产品开发的战略整合提供依据。具体来说，我们想理解工程师如何使用 GitHub Copilot，以及它的采用是否带来可衡量的工程生产力收益。此外，本研究还试图厘清在企业环境中有效衡量工程生产力所需的条件。

为了便于实际业务决策，我们的现场研究在设计上尽量减少对既有工程实践的干扰，并真实反映现实世界条件，而非人为的实验室环境。我们的实验设计遵循三条指导原则：第一，在满足学术好奇心的同时产出可执行的业务洞见；第二，把参与工程师的负担降到最低，避免引入仅为研究而设的多余流程；第三，尽可能准确地测量相关数据与行为，以反映真实运营场景。

测量行为本身就会改变系统的状态，这一现象从电路到量子力学，在不同领域都被观察到。这种情况在社会与管理情境中尤为明显：一旦设立特定指标，就可能影响行为，甚至诱发策略性动作，或通过「玩指标」来获取好看的结果 [6], [13]。认识到尽可能减少这类反应性效应、并获取反映真实实践的数据的重要性，我们在整个研究过程中都优先保证对参与者透明，说明数据收集目标、数据关联方式与保密安排。为进一步减轻研究引发行为改变，我们与许多前瞻性主动监测参与者活动的观察性研究不同，主要分析依赖的是所招募参与者的历史工程度量数据。

**组织欧姆定律。** 本研究的实验设计与方法受到 OOL 框架的启发，这是我们此前提出、用于分析工程生产力的一个概念 [15], [16]。该框架把电路与组织系统作类比：结果电流（outcome current），因此也就是组织生产力，正比于结果—产出效率与组织潜能，反比于组织阻力。通过用可量化的时间分配来近似组织阻力，该定律表明：工程生产力与花在核心软件工程活动（即编码与测试）上的时间占比、工程师的平均相对动机水平、以及工程师的平均相对技能水平正相关。

借助这一框架，我们测量了采用 GitHub Copilot 前后，工程师在多个领域的时间分配变化，包括编码、测试、沟通、等待决策与依赖、文档、工程流程、公司流程，以及工程基础设施的低效 [14], [21]；同时也测量了相对员工动机 [12], [17], [18] 与技能评分。这些数据让我们能够以一种既有理论依据、又符合直觉的方法，全面评估采用 GitHub Copilot 的影响。

**我们的贡献。** 第一，我们给出一项整体性的、真实世界的企业级 GitHub Copilot 影响评估，识别并提供了「效率—吞吐量缺口」的实证证据。我们的发现挑战了「AI 立即带来生产力收益」的流行叙事：尽管观察到工程师动机与自我感知技能提升、工作时长下降，我们并未发现关键工程度量（如月度拉取请求数与代码行数）立即增长。这一结果凸显出：要真正释放 AI 驱动工具的潜力，需要持续创新并优化软件工程运作方式。第二，我们提出一套多方法框架，用于在企业环境中整体评估 AI 工具的影响。通过整合 OOL 框架、以人为中心的问卷、客观工程度量与参与者信息，本研究提供了一套企业可采纳、并持续评估 AI 影响的方法论。

## 我们的方法

**实验设计。** 本现场研究在 Okta, Inc. 的工程组织内开展。Okta 是一家美国上市企业软件公司，为现代安全提供云原生身份与访问管理。为了让研究具有直接的实践影响，我们把研究同公司内部的 GitHub Copilot 推广整合在一起。这一真实世界背景使我们得以用多方法定量设计，全面评估 Copilot 对多个工程团队的影响。该方法将三类数据进行三角互证：主观的 Copilot 生产力问卷、客观的 GitHub Copilot 与工程度量，以及参与者背景信息。

为控制其他 AI 工具带来的混杂变量，我们利用了公司既有的政策：不鼓励把公司代码暴露给外部、未经批准的 LLM。推广前的一次初步调查证实了该政策的有效性——其他 AI 工具的使用极少，这让我们对基线测量有很高的信心（详见附录 A.1）。由于 GitHub Copilot 是研究期间唯一在全公司规模正式部署的 AI 开发者工具，我们可以把观察到的变化主要归因于它的引入。

**工程生产力问卷。** 为了解 GitHub Copilot 在组织内初步推广后对工程生产力的影响，我们在推广数月后，使用商用在线问卷平台 Qualtrics 开展了调查。问卷收集了参与者的背景信息、他们在各项工作活动上的平均每周时间分配、动机与技能的李克特量表评分、使用 Copilot 前后对代码质量与测试频率的李克特量表评估、Copilot 使用频率、感知到的 Copilot 有用领域、对 Copilot 生产力提升的感知评分、对使用它的顾虑，以及关于工程生产力或 GitHub Copilot 体验的开放式意见（问卷样例见附录图 A1）。问卷被设计得尽量简短，约需五分钟完成。

参与者招募与多个工程团队的 GitHub Copilot 部署工作协同进行。2024 年 11 月 18 日至 12 月 20 日期间，我们通过 Slack 和电子邮件，邀请了 261 位在 2024 年 7 月至 9 月间获得 Copilot 许可的人（招募信息见附录图 A2）。我们收到 97 份回复，其中 95 份包含电子邮件地址，使我们能把问卷数据与他们的 GitHub Copilot 及工程度量关联起来。参与调查完全自愿、无报酬。（受访者的从业经验分布见附录图 A3。）

**GitHub Copilot 与工程度量。** 整个研究过程中，我们始终保持数据关联方面的透明。问卷工具与招募沟通（通过 Slack 和电子邮件）都明确说明：参与者的电子邮件地址仅用于把问卷回复与 GitHub Copilot 及工程度量关联起来，服务于这项关于工程生产力的研究。我们也向参与者保证，所有数据都将匿名分析并严格保密。因此，我们以参与者的电子邮件地址作为唯一标识，把他们的主观问卷输入与客观度量关联起来。

我们使用 Faros.ai [a] 提取相关度量。Faros.ai 是一个商用工程数据平台，通过表述性状态转移 API（REST API）与公司的一系列工程软件应用（如 GitHub 和 JIRA）集成。Faros.ai 会把获取到的数据转换为其专有模式，使我们能通过其仪表板查询并提取关键度量。度量包括 Copilot 激活日期、Copilot 使用统计、拉取请求（PR）数量、PR 评论数、PR 审查数，以及贡献的代码行数（LOC）。为建立采用 Copilot 前的基线，我们使用 2024 年 4 月、5 月和 6 月的数据；采用 Copilot 后的数据则以 2024 年 9 月、10 月和 11 月为代表。

**参与者信息。** 工程生产力问卷包含关于参与者工程经验的问题，收集了软件开发从业年限、主要编程语言等变量。为了提供更多背景，我们用公司 Workday 系统中的信息丰富了问卷数据，包括入职日期、职位名称、职级、工作地点和所属工程团队等变量。

### 数据准备

**数据清洗。** 收集到的数据集经过清洗与预处理，以处理问卷回复和度量数据中可能的错误与不一致。这一过程包括校正参与者标识符、核查并调整自报数据中的异常值，以及处理不完整回复。我们采取的数据策略是保留所有回复与度量数据以供进一步分析。虽然这会带来更细致的处理与分析工作，但能最大化数据集规模——考虑到我们的样本量中等，这一点至关重要。更重要的是，这种做法更准确地反映了真实世界工程生产力测量的复杂性，能识别边缘情况并通过后续分析加以处理。最终数据集包含 95 份有效回复，其中 74 份在前后对比分析中完整可用。（数据清洗流程详见附录 A.3。）

按月提取的原始 GitHub Copilot 与工程度量本身存在波动。为缓解这些波动、并考虑入职与离职，我们对采用 Copilot 前（2024 年 4 月至 6 月）与采用后（2024 年 9 月至 11 月）两个时期都采用了三个月滚动平均。随后，我们统计每位参与者的有效月度数据点数量，并基于这些有效月份计算均值与标准差。把采用后的三个月平均度量，与仅按个人获得 Copilot 许可之后月份计算的度量相对比，得到的结论相似。因此，后续分析统一使用 2024 年 9 月至 11 月的三个月平均工程度量数据，以保证一致性并减少波动。

**数据集成。** 为整合来自多个来源与系统的数据，我们以参与者的电子邮件地址作为唯一标识进行记录关联。数据清洗、连接流程与洞见分析都通过 Jupyter Notebook 中的 Python 实现。数据准备完成后，我们生成了一个 CSV 格式的统一数据集，包含问卷回复、GitHub Copilot 与工程度量，以及丰富的参与者信息。这个集成数据集为每位参与者最多包含 150 个直接属性与派生属性，支持对受访者的工程生产力进行多维度分析。为清晰起见，我们聚焦于与 GitHub Copilot 影响相关的分析与结果。

## 评估 GitHub Copilot 的影响

**GitHub Copilot 使用情况。** 问卷中有一道题询问参与者近期的 GitHub Copilot 使用情况：「你最近使用 GitHub Copilot 的频率如何？」我们还在同一时期收集了客观的 GitHub Copilot 使用度量。分析显示，参与者之间的 Copilot 使用差异很大：在 Copilot 部署后的三个月里，有 7% 的人报告未使用，如图 1 所示。为评估自报使用情况（橙色柱）与实测使用情况（蓝色柱）之间的一致性，我们对比了这两组数据。尽管测量方法、数据来源与数据类型本身存在差异，统计检验显示二者存在统计显著（p < 0.001）、中等偏大（Pearson's r = 0.48，Spearman's ρ = 0.44）的相关性 [9]，这说明参与者对 Copilot 使用行为的感知与实际情况总体一致。本质上，这一对比起到了质量检查的作用，强化了整个研究的基础，使我们能更有信心地继续分析其他自报问卷题项的数据完整性。

*图 1：自报与实测的月度 GitHub Copilot 使用情况直方图。*

为评估潜在的问卷参与偏差，我们还将受访者的客观 Copilot 使用度量与公司内全部获得许可的 Copilot 用户进行了比较。结果显示，受访者使用 Copilot 的可能性显著更高，使用频率也更高。因此，本文呈现的发现可能比全体用户的实际体验更偏乐观。

**采用 GitHub Copilot 前后的对比。** 为确定评估 GitHub Copilot 问卷回复与工程度量配对前后数据的合适统计检验，我们实施了如下数据分析。在通过 Shapiro-Wilk 正态性检验与对称性检查（中位数的平均绝对偏差 ≤ 标准差）之后，对 Copilot 用户的配对差值采用以下三种统计检验之一：

- 若差值通过正态性检验（p > 0.05），采用配对 t 检验，并以 Cohen's d 作为效应量度量变化幅度。
- 若差值不服从正态分布但对称，采用 Wilcoxon 符号秩检验，并以秩双列相关（rank-biserial correlation，r）作为效应量度量变化幅度。
- 若差值不对称，采用符号检验，以实现为对正负差值计数进行双侧二项检验，并以 Cohen's g 作为效应量度量变化幅度。

这些统计检验的结果可视化于图 2 与图 3。对于每个回复或度量，对应的子图会展示前后均值、所执行的统计检验类型、得到的 p 值、效应量检验及其对应值，以及数据对数量。若所选统计检验得到统计显著的结果（p ≤ 0.05），该子图中的前后柱条为绿色；否则为粉色。

**工程师时间分配。** 为理解工程师的时间分配，我们把工程活动划分为若干不同类别，并请受访者报告每周花在各类别上的时间。图 2（a–j）展示了使用 GitHub Copilot 前后，报告的平均时间分配及相应的 95% 置信区间。采用 Copilot 后，参与者报告在所有活动类别上的平均耗时都下降了。时间节省最多的是编码（每周 1.06 小时）与测试（每周 1.56 小时）。总体而言，参与者报告工作与生活平衡改善，平均每周工作时长从 44.77 小时降至 40.83 小时。在上下文切换（context shifting）、编码、文档、测试以及总工作时长上，观察到统计显著（p ≤ 0.05）的下降。这些下降的效应量很大，秩双列相关 r 在 -0.51 到 -0.90 之间 [9]，表明影响显著。相比之下，花在更偏人际/协作领域的时间——如沟通、等待决策与依赖、公司流程、工程流程，以及工程基础设施的低效——没有显示统计显著变化。

*图 2：Copilot 用户在采用 GitHub Copilot 前后，工程师时间分配、动机与技能的比较。*

数据还显示，参与者约 30% 的工作时间用于编码，10–15% 用于测试，略多于 50% 用于其他活动。按职级分析工作时间分配，显示出统计显著的依赖关系（方差分析（ANOVA），p ≤ 0.05）。初级工程师报告把 50–70% 的时间用于编码与测试，而高级工程师在这类任务上的时间占比不足 30%（见附录图 A4）。这一模式符合工程职业发展的通常预期：级别更高的角色更多涉及主导项目、参与技术战略、跨组织协作与指导他人，而非直接写代码和测试。

**工程师动机与技能。** 图 2（k–l）展示了工程师动机与技能的前后评分及 95% 置信区间。参与者报告，在采用 GitHub Copilot 后，其动机与自我感知技能水平都有统计显著的提升。这些提升伴随着非常大的效应量（动机的秩双列相关 r 为 0.95，技能为 1.00）[9]。

**拉取请求。** 图 3（a–h）展示了前后三个月的月均 PR 数量、PR 周期时间（cycle time）、月度 PR 评论数（收到的评论）、月度 PR 审查数（执行的审查）及其相应的 95% 置信区间。与现有研究和营销中的发现相反——或许也出乎意料——只有月度 PR 审查数显示出统计显著的增加；其他 PR 度量均无显著改善。需要指出的是，虽然我们在分析月度 PR 数量时把每个 PR 同等对待，但 PR 的工作量可能差异很大。因此，在未来分析中纳入合适的 PR 元数据（如 PR 规模）可能会更好地反映工程产出。

*图 3：Copilot 用户在采用 GitHub Copilot 前后，工程度量的比较。*

**月度代码行数。** 月度 LOC 度量按每位参与者三个月平均 LOC 的均值计算。我们提取了多种 LOC 变体，包括新增行、删除行、diff 大小与净新增行。在实践中，原始 LOC 被证明是个体编码投入不可靠的代理指标——采用 Copilot 前的平均值超过了每月新增 30,000 行这一高得不合理的水平。对个人贡献的分析发现，LOC 由特性编码之外的多种代码开发活动构成。例如：特性开发团队可能主要从事应用逻辑的编写（这正是受控环境中最常被研究的那类编码）；工程平台团队可能只需极少人工输入就生成大量配置代码；技术债团队在重构期间也可能产生大量 LOC 变更。

为分离出能够指示直接工程编写的 LOC，我们曾考虑只关注特性开发团队或代码仓库。但这一做法并不充分，因为特性代码与依赖、配置、元数据代码常常共处同一仓库，且往往缺乏一致的目录或命名约定，难以可靠地自动拆分。作为替代方案，我们尝试依据 LOC 变更规模过滤 PR，假设超大的变更不太可能代表逐行直接编码的投入。参考 PR 审查的行业最佳实践，并结合我们就常见组织实践对工程师的访谈，我们开发了一条启发式规则来识别可能包含工程编写代码的 PR：(新增+删除行数 < 801) 或 (新增+删除行数 < 1001 且评论数 > 5) 或 (新增+删除行数 < 3001 且评论数 > 7) 或 (新增+删除行数 < 5001 且评论数 > 10) [3], [4], [7]。不符合该启发式规则的 PR 的 LOC 贡献被排除在参与者的月度 LOC 总量之外。这些重新计算的 LOC 度量值对启发式规则的变化并不过分敏感。此外，经过这一过滤后重新计算的各种 LOC 度量，其数值落入了对直接编码投入更合理的区间 [16], [19]，如图 3（e–h）所示。尽管如此，与我们在 PR 度量上的发现一致，无论是原始 LOC 度量变体还是重新计算的版本，在采用 Copilot 后都没有显示统计显著变化。

此外，对于被分配了 Copilot 许可但并未使用的参与者，我们观察到问卷反馈没有报告任何变化，任何工程度量也没有统计显著变化，如附录图 A5 与 A6 所示。不过，这一未使用者群体样本量较小，因此这些零结果应谨慎解读。

**帕累托洞察。** 我们还检验了一个与既有文献一致的假设 [20]：AI 工具对经验较少的工程师帮助更大。这项分析的目的是看 Copilot 是否让工作产出的分布更均匀。为检验这一点，我们对使用 Copilot 的参与者，在采用前后进行了 PR 数量的帕累托分析（图 A7）。在采用 Copilot 之前，46%（74 人中的 34 人）的参与者贡献了总 PR 产出的 80%。在实施 Copilot 之后，这一比例上升到 53%（74 人中的 39 人）的参与者，对应了略有增加的总 PR 产出的 80%。观察到的比例变化意味着，Copilot 可能让工程师之间的 PR 贡献分布更均匀，可能让初始 PR 产出较低的人受益。然而，统计分析发现，前后两个分布之间的差异并不统计显著。

**GitHub Copilot 的收益与顾虑。** 为评估 GitHub Copilot 的收益与顾虑，我们用多选题调查了参与者。第一个问题是「你认为 GitHub Copilot 在哪些方面有用？」，选项与工程师时间分配、动机和技能对齐，并包含从简单到复杂的编码任务细分（图 4 a）。参与者报告，Copilot 在样板代码、函数模板、查询、配置文件和测试方面最有用；但在开发前端组件与后端服务、编写复杂逻辑或算法，以及支持以人为中心的企业开发活动方面能力较弱。第二个问题是「被分配席位后，你不使用 GitHub Copilot 的原因是什么？」，结果显示不使用的主要原因是担心 Copilot 的准确性，以及没有时间、缺乏使用 Copilot 的知识（图 4 b）。尽管存在这些局限，94 位参与者对 GitHub Copilot 对整体生产力影响的评分为李克特量表中平均 3.95 分（满分 5 分），表明总体感知相当正面。

*图 4：工程师对 GitHub Copilot 的看法：(a) 收益（n=92）与 (b) 顾虑（n=79）。*

随后，我们试图验证：在编码、测试等活动中观察到的自报时间减少（图 2），是否与这些感知收益存在统计关联。我们的假设是：认为 Copilot 对某项活动（例如「测试」）有用的工程师，应该正是报告该项活动时间减少的那批工程师。为检验该假设，对每一项工程师时间分配活动，我们计算了时间分配变化与 GitHub Copilot 收益提及之间的数值相关与二元 Pearson 相关及其对应 p 值，以检验基本关联。此外，我们进行了卡方检验（χ² 检验），评估二元时间分配变化与收益提及之间的关联。最后，我们用双样本 t 检验，比较了提及某活动 Copilot 收益与未提及的工程师之间的平均时间分配变化。

我们的分析显示，对于上下文切换、工程流程、测试和工程基础设施低效这几类，时间分配变化与收益提及之间存在相对较强的负数值相关。上下文切换、编码、文档、工程流程、测试和工程基础设施低效则表现出相对较强的二元相关。卡方检验表明，上下文切换、编码、文档、工程流程、测试和工程基础设施低效的二元变化，与其对应的收益提及之间存在显著关联。此外，t 检验显示，在提及与未提及收益的两组之间，上下文切换、编码、工程流程和测试的平均度量变化值存在显著差异（详见附录表 A1）。

综合来看，这些分析表明：在采用 GitHub Copilot 前后出现统计显著下降的四项时间分配活动（上下文切换、编码、文档和测试），与感知到的 Copilot 收益之间存在合理的关系。

## 讨论

这项工作对 GitHub Copilot 的采用进行了多维度考察，为软件生产力测量以及该工具对企业软件开发的影响提供了洞见。一方面，我们展示了 OOL 作为一种实用且整体的框架的价值：它把工程师活动（时间分配）、心理状态（动机）与能力（技能）同工程度量结合起来，用以理解工程生产力。另一方面，我们的真实世界研究凸显了准确衡量工程生产力时固有的空白，并提示了一些更严格实践可能具有的价值，例如统一的仓库目录标注、拉取请求规模标注，以及对 AI 生成代码的识别，以改进未来的评估。

就 GitHub Copilot 的影响而言，我们的发现揭示了「个体效率」与「组织吞吐量」之间的关键区别。虽然工程师对 GitHub Copilot 的使用差异很大，但该工具确实促进了感知到的工程师价值提升，减少了花在各种工程活动上的时间，并提升了动机与感知技能。然而，我们并未观察到它与关键工程度量的增长之间存在立即的直接关联。这带来了个体效率提升（同样的工作用更少时间完成），但没有统计显著的组织吞吐量提升（月度 PR 数量或代码行数没有增加）。根据 OOL 框架，我们假设这类工具带来的生产力提升分三个阶段发生：

1. *效率收益：* 工具提升了平均个体潜能（动机、技能），并降低了在编码、测试等特定任务上的阻力。然而，整体结果电流保持不变。效率收益让个体获益，带来更好的工作与生活平衡。我们的数据提示出现了第一阶段的早期迹象，但尚未进入第二阶段。
2. *生产力收益：* 要提升结果电流，组织必须自觉地降低总阻力，并进一步提升个体潜能。这需要提升开发者技能以充分利用工具功能、调整生产力预期，并优化开发工作流，使其与 AI 增强后的开发者能力相匹配。
3. *组织优化：* 组织可以重新设计其「组织电路」，以降低以人为中心的阻力。这涉及结构性变革，例如创建更自主的团队或扩大个体职责范围，以减少沟通与决策开销，并探索有效的人机协作模式。

这项工作强调，要真正实现组织生产力收益，仅仅部署一个 AI 驱动工具是不够的。它需要工程与管理层有意识地付出努力去适应，去了解这个工具在自身特定问题上能做与不能做什么（因为工具功能迭代很快），并重塑团队、工程流程与基础设施，以捕获潜在效率。这些发现指导了我们组织研究后的策略。认识到它对个体的强烈正面影响后，我们取消了管理审批以加速 Copilot 采用，同时持续监测使用情况。我们开始分享最佳实践以提升工具利用率，建立对其当前局限的共同理解，并识别新的挑战。此外，我们正在把 AI 影响测量嵌入常规工程流程，并引入更广泛的 AI 驱动工具，如 Copilot agent 模式和各种 vibe-coding 应用。这一努力代表着工具、团队、流程与基础设施共同发明（co-invention）的开端，而这正是充分探索并实现 AI 驱动生产力提升潜力所必需的。

尽管本研究提供了全面的分析与有洞见的发现，其研究范围仍存在若干局限。第一，研究在单一公司内进行，参与者数量中等，这可能限制结果的可推广性。此外，样本量意味着某些统计不显著的结果可能源于统计功效不足，而非效应不存在。第二，由于研究捕捉的是 GitHub Copilot 的初始推广阶段，观察到的影响可能无法完全反映其长期效应。不过，我们随后对参与者 2024 年 12 月至 2025 年 5 月的 PR 与 LOC 监测显示没有统计上的改善，这支持了一个观点：仅靠时间不足以把个体效率转化为组织吞吐量。第三，我们使用的客观产出度量（如月度 PR 数与月度 LOC）充其量只是工程生产力的代理指标，无法刻画工程产出的全貌。第四，这项工作主要关注对工程产出度量的影响，而非更广泛的业务成果，如加快上市时间或提升产品质量。第五，分析基于组织当时所采用的 GitHub Copilot AI 辅助编码功能，包括自动补全与聊天。鉴于 AI 驱动开发工具演进迅速，更高级能力（如对企业代码库的检索增强生成（RAG）或更深的工程工作流集成）的影响值得单独研究。这些 AI 驱动工具的持续进步可能会改变其影响。对于未来工作，我们建议优先开展跨不同组织的纵向研究，考察 AI 驱动工具对工程生产力的长期影响，从而为研究者和从业者提供有价值的技术、商业与经济洞见。

## 总结

这项关于 GitHub Copilot 生产力影响的现场研究，超越了「立即获得收益」的炒作，识别出「效率—吞吐量缺口」，揭示了比既有研究和营销中常见说法更微妙的现实。我们的发现强调了组织在把 AI 驱动的个体效率提升——我们观察到的是工程师情绪改善与工作时长下降——转化为即时且可量化的组织生产力吞吐量时所面临的挑战：在产出度量上，我们没有发现统计显著的改善。通过整合组织欧姆定律框架、以人为中心的问卷与客观工程度量，本研究还提供了一套稳健且可复现的方法论。它为企业提供了一套实用工具，使其能够超越一次性的快照，转向对 AI 不断演变影响的持续评估流程，为迭代式共同发明、并最终实现切实的工程生产力提升铺平道路。
