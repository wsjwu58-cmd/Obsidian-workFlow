# ECC

你的智能体可以编写代码，但ECC赋予它一个协调的工程系统和工具箱：它在构建之前进行规划，通过测试验证更改，从全新上下文中审查自己的工作，记住重要事项，并将重复的成功转化为可复用的技能和工作流程。

```text
规划 -> 测试 -> 实现 -> 审查 -> 验证 -> 记忆 -> 改进
```

无需在每次提示中重建该流程，你只需安装一次，使其成为智能体工作方式的一部分。

> 优化上下文窗口。持久化其他一切。

ECC是MIT许可的开源项目。目前它与Claude Code配合最佳，同时提供一流的Codex支持，并适配Cursor、OpenCode、Gemini、Zed、GitHub Copilot、Antigravity、Qwen及其他工具链。

可访问67个智能体、281项技能和94个传统命令适配器，以及钩子、规则、记忆、持续学习和AgentShield安全扫描。这些智能体专精于规划、审查、构建修复、安全、架构和领域工作。

| 包含内容         |       数量 | 提供功能                                                                              |
| ---------------- | ----------: | ------------------------------------------------------------------------------------ |
| 智能体           |   67个智能体 | 规划、审查、构建修复、安全、架构和领域工作                                            |
| 技能             |  281项技能 | TDD、研究、安全、文档、前端、数据、机器学习、运维等                                   |
| 命令             | 94个命令 | 在ECC转向技能优先界面的过程中提供便捷入口点                                          |
| 钩子与记忆       |     运行时 | 执行强制、会话摘要、持续学习、直觉和上下文控制                                        |
| 规则             |   选择性 | 按语言或项目选择始终加载的标准                                                        |
| AgentShield      |    包含 | 扫描提示、钩子、MCP配置、权限、密钥和智能体文件                                      |

## 安装ECC

### 每个工具链仅选择一种路径

你可以同时将ECC与Claude Code、Codex及其他工具链一起使用。为每个工具链选择一种安装方式：

- **可行：** Claude Code插件 + Codex同步
- **避免：** Claude Code插件 + 完整版Claude手动安装
- **避免：** Codex同步 + Codex市场插件

**推荐默认方案：** 为Claude Code安装Claude Code插件，并为Codex使用支持的同步流程。**不要叠加安装方式。** 在同一工具链中安装两次ECC可能会导致技能、命令、钩子或配置重复；而在多个工具链中各安装一次则不会。

如果你已经叠加了多种安装方式且出现重复情况，请直接跳至[重置/卸载ECC](#reset--uninstall-ecc)。

### Claude Code

在Claude Code中运行以下命令：

```text
/plugin marketplace add https://github.com/affaan-m/ECC
/plugin install ecc@ecc
```

这将安装ECC的技能、代理、命令和插件管理的钩子。Claude Code插件无法分发`rules`，因此只添加你实际需要的规则包：

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
mkdir -p ~/.claude/rules/ecc
cp -R rules/common ~/.claude/rules/ecc/
cp -R rules/typescript ~/.claude/rules/ecc/  # 替换为你的技术栈
```

从`rules/common`加上你实际使用的一种语言或框架包开始。如果安装了插件，之后不要再运行`./install.sh --profile full`。

<details>
<summary><strong>更喜欢settings.json？以声明方式添加市场</strong></summary>

直接添加到你的`~/.claude/settings.json`中：

```json
{
  "extraKnownMarketplaces": {
    "ecc": {
      "source": {
        "source": "github",
        "repo": "affaan-m/ECC"
      }
    }
  },
  "enabledPlugins": {
    "ecc@ecc": true
  }
}
```

这与上面两条`/plugin`命令的效果相同。
</details>

<details>
<summary><strong>命名与迁移说明（ecc@ecc、affaan-m/ECC、ecc-universal）</strong></summary>

ECC有三个公开标识符，它们不可互换：

- GitHub源仓库：`affaan-m/ECC`
- Claude市场/插件标识符：`ecc@ecc`
- npm包：`ecc-universal`

这是有意为之。Anthropic市场/插件安装以规范插件标识符为键，因此ECC使用`ecc@ecc`来保持工具名称和斜杠命令命名空间足够短，以满足严格的Desktop/API验证器要求。旧帖子可能仍显示之前的长市场标识符；仅将其视为遗留别名。另外，npm包保持为`ecc-universal`，因此npm安装和市场安装有意使用不同名称。

npm版本按版本标签发布，而非按提交发布，因此`ecc-universal`跟踪发布版本（2.1、2.2等），而非每次推送到`main`。如果你想要最新版本，请从git安装。

如果你的本地Claude设置被清除或重置，这并不意味着你需要重新购买任何东西。先运行`node scripts/ecc.js list-installed`，然后运行`node scripts/ecc.js doctor`和`node scripts/ecc.js repair`，再重新安装。这通常能恢复ECC管理的文件，而无需重建你的设置。
</details>

### Codex应用与CLI

Codex的可靠ECC设置是同步流程。先运行一次Codex，以确保`~/.codex/config.toml`存在。同步会保留你现有的Codex文件，创建带时间戳的备份，并将ECC的`AGENTS.md`、技能、提示、代理和参考配置合并到`~/.codex`中：

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
npm install
bash scripts/sync-ecc-to-codex.sh
```

你也可以直接在Codex中打开ECC仓库，进行项目本地设置。Codex会读取根目录的`AGENTS.md`和`.codex/`中的受信任项目配置，无需全局同步。

关于仓库导航、所有权展示和PR差异包指南，请阅读[Codex ECC导航地图](docs/CODEX-NAVIGATION-GUIDE.md)。

<details>
<summary><strong>Codex插件市场（ECC实验性）</strong></summary>

Codex官方支持插件市场，ECC发布了一个仓库市场：

```bash
codex plugin marketplace add affaan-m/ECC
codex plugin marketplace list
```

重启Codex，然后从插件目录安装或启用`ecc`。不要在Codex同步流程之上添加市场插件。市场注册在Codex中是稳定的，但ECC当前的插件包引用了共享仓库内容，这些内容可能不会被复制到Codex的安装缓存中。在该上游缓存行为解决之前，当你需要所有ECC技能可靠可用时，请使用上述同步流程。
</details>

从 ECC 检出后，使用以下命令验证已安装的插件缓存：

```bash
node scripts/codex/check-plugin-cache.js
```

有关当前限制和跟踪问题，请参阅 [.codex 插件说明](.codex-plugin/README.md)。
</details>

## 高级安装选项

这些选项直接保留在主安装路径下方，这样当默认设置不适合时，您无需在 README 中查找。

<details>
<summary><strong>无钩子运行时的低上下文安装</strong></summary>

### 低上下文 / 无钩子路径

当您需要 ECC 的规则、代理、命令、平台配置和核心工作流，但不需要运行时钩子时，请使用此选项：

```bash
./install.sh --profile minimal --target claude
# 或者，无需先克隆
npx ecc-install --profile minimal --target claude
```

Windows：

```powershell
.\install.ps1 --profile minimal --target claude
```

此配置文件有意排除 `hooks-runtime`。

Claude 手动安装会将每个技能直接放置在 `~/.claude/skills/<skill-name>/`（或 `claude-project` 的 `.claude/skills/<skill-name>/`）下，以便 Claude Code 可以发现它。升级旧版 ECC 手动安装时，安装程序仅迁移 ECC 安装状态中记录的嵌套 `skills/ecc/` 文件。如果扁平技能目录归用户所有，ECC 会保留它，打印冲突警告，并保留任何旧的管理副本以便安全卸载，而不是覆盖用户文件。

对于禁用钩子的正常核心配置文件：

```bash
./install.sh --profile core --without baseline:hooks --target claude
```

仅当您需要时，稍后添加钩子运行时：

```bash
./install.sh --target claude --modules hooks-runtime
```
</details>

<details>
<summary><strong>仅选择您需要的组件</strong></summary>

### 首先找到合适的组件

向打包的顾问询问哪些组件适合您的工作：

```bash
npx ecc consult "security reviews" --target claude
```

它会返回匹配的组件、相关配置文件以及预览/安装命令。如果您想检查确切的文件计划，请在安装前使用预览命令。

你也可以安装明确的技能或能力：

```bash
./install.sh --target claude --skills tdd-workflow,security-review
npx ecc install --profile minimal --target claude --with capability:machine-learning
```

手动逐个组件复制同样可行。每个组件完全独立：

```bash
# 仅代理
cp agents/*.md ~/.claude/agents/

# 规则目录（通用 + 语言特定）
mkdir -p ~/.claude/rules/ecc
cp -r rules/common ~/.claude/rules/ecc/
cp -r rules/typescript ~/.claude/rules/ecc/   # 选择你的技术栈

# 仅核心/通用技能（Claude Code 从 ~/.claude/skills 的直接子目录加载技能；
# 不要将手动安装嵌套在 ~/.claude/skills/ecc/ 下）
mkdir -p ~/.claude/skills
cp -r .agents/skills/* ~/.claude/skills/
cp -r skills/search-first ~/.claude/skills/

# 可选：迁移期间维护斜杠命令兼容性
mkdir -p ~/.claude/commands
```

#### 安装钩子

不要将原始仓库的 `hooks/hooks.json` 复制到 `~/.claude/settings.json` 或 `~/.claude/hooks/hooks.json`。该文件面向插件/仓库；请使用安装程序，以便钩子命令路径被正确重写：

```bash
bash ./install.sh --target claude --modules hooks-runtime
```

这将把解析后的钩子写入 `~/.claude/hooks/hooks.json`，并保持任何现有的 `~/.claude/settings.json` 不变。

如果你通过 `/plugin install` 安装了 ECC，不要将这些钩子复制到 `settings.json` 中。Claude Code v2.1+ 已自动加载插件的 `hooks/hooks.json`，在 `settings.json` 中重复它们会导致重复执行和跨平台钩子冲突。

在 Windows 上，Claude 的配置根目录是 `%USERPROFILE%\\.claude`；使用以下命令安装钩子运行时：

```powershell
pwsh -File .\install.ps1 --target claude --modules hooks-runtime
```

#### 配置 MCP

Claude 插件安装有意不自动启用 ECC 捆绑的 MCP 服务器定义。这避免了在严格的第三方网关上出现过长的插件 MCP 工具名称，同时保持手动 MCP 设置可用。

使用 Claude Code 的 `/mcp` 命令或 CLI 管理的 MCP 设置进行实时 Claude Code 服务器更改；Claude Code 将这些选择持久化在 `~/.claude.json` 中。对于仓库本地 MCP 访问，将所需的 MCP 服务器定义从 `mcp-configs/mcp-servers.json` 复制到项目范围的 `.mcp.json` 中。

ECC 仅提供一个默认连接器（`chrome-devtools`）；其他所有内容都是包装 CLI/REST API 的技能或可选目录条目。相关规则和 2026 年 6 月审计（该审计淘汰了之前的六个默认项）见 [docs/MCP-CONNECTOR-POLICY.md](docs/MCP-CONNECTOR-POLICY.md)。

如果你已经运行自己的 ECC 捆绑 MCP 副本，请设置：

```bash
export ECC_DISABLED_MCPS="chrome-devtools"
```

ECC 管理的安装和 Codex 同步流程将跳过或移除这些捆绑服务器，而不是重新添加重复项。`ECC_DISABLED_MCPS` 是 ECC 安装/同步过滤器，不是实时的 Claude Code 开关。

**重要：** 将 `YOUR_*_HERE` 占位符替换为你的实际 API 密钥。

### Itô 计算 CLI 桥接

`ecc ito` 委托给单独安装的规范 Itô 客户端；ECC 不维护第二个 API 客户端或浏览器交接。可用的操作包括 `ecc ito auth`、`ecc ito find`、`ecc ito status` 以及单独门控的 `ecc ito evals`。匹配的 MCP 工具仍然是 `ito_auth`、`ito_find` 和 `ito_status`；节点资格认证仅限 CLI。

`ito-compute-cli` 包目前尚未发布。从 Itô 运行时仓库（在桌面端加固期间为私有；设计合作伙伴可获得访问权限）中的 `cli/ito-compute-cli` 下本地构建它，运行 `npm ci` 和 `npm run check`，然后将 `ECC_ITO_CLI_EXECUTABLE` 设置为该构建的绝对 `dist/bin/ito.js` 路径。从 1Password 或启动环境注入 `ITO_API_KEY`。ECC 不会通过 `PATH` 发现这个包含凭据的客户端。有关完整的 RFQ 权限和 MCP 设置契约，请参阅 [`ito-compute` 技能](skills/ito-compute/SKILL.md)。

`find` 提交一个实时的已认证 RFQ。它不预留容量。`evals` 需要同时设置 `ITO_ENABLE_SIXTYTWO_LIVE=1` 和 `--live-sixtytwo`，单独安装 `sixtytwo-cli==0.3.33`，明确的节点列表，以及一个现有的绝对配置目录。它不能租赁、启动、恢复、修复或购买。ECC 不暴露报价锁定、购买、工作负载或推理路径，并且它绝不会用本地结果替代缺失的客户端或失败的实时调用。

<summary><strong>重置、修复或卸载</strong></summary>

### 重置 / 卸载 ECC

如果 ECC 感觉重复、侵入或损坏，请在重新安装前检查受管状态：

```bash
node scripts/ecc.js list-installed
node scripts/ecc.js doctor
node scripts/ecc.js repair
node scripts/ecc.js uninstall --dry-run
```

直接卸载：

```bash
node scripts/uninstall.js --dry-run
node scripts/uninstall.js
```

插件用户应从 Claude Code 中移除插件，然后仅删除他们手动复制且不再需要的规则文件夹。ECC 仅删除其安装状态中记录的文件。它不会声称拥有您工具链目录中的无关文件。

如果您叠加了多种方法，请按以下顺序清理：

1. 移除 Claude Code 插件安装。
2. 从仓库根目录运行 ECC 卸载命令，以移除安装状态管理的文件。
3. 删除您手动复制且不再需要的任何额外规则文件夹。
4. 使用单一路径重新安装一次。

## 为什么选择 ECC？

| 没有系统                                        | 使用 ECC                                                              |
| ------------------------------------------------------- | --------------------------------------------------------------------- |
| 计划消失在聊天历史中                       | 计划在实现开始前成为可编辑的工件          |
| “请使用 TDD” 是模型可能忘记的指令 | TDD 成为带证据的门控 RED -> GREEN -> REFACTOR 工作流 |

| 同一上下文编写并审查代码            | 新上下文审查者寻找回归和盲点        |
| 记忆意味着保存大量对话记录              | 会话被提炼为摘要、直觉和可复用技能 |
| 质量检查依赖于提醒                    | 钩子可以在提示词之外强制执行确定性检查 |
| 代理配置默认被信任                    | AgentShield 将工具链本身视为攻击面进行扫描 |

### TDD：测试驱动开发

```text
/ecc:plan "添加基于使用量的计费提醒"
  -> 确认或编辑计划
  -> 激活 tdd-workflow
  -> 在实现前捕获 RED 证据
  -> 实现直到 GREEN
  -> 从新上下文进行审查
  -> 修复发现的问题并添加回归测试
  -> 验证构建、lint、类型和测试
```

结果不仅仅是代码，而是一系列证据：计划、失败的测试、通过的测试、审查发现和最终验证。

### 技能保持上下文聚焦

规则、技能、代理和钩子解决不同的问题。保持这些职责分离是 ECC 在不将整个仓库倾倒入每个会话的情况下增加能力的方式。

| 概念 | 作用 | 上下文行为 |
|---|---|---|
| 技能 | 可复用工作流，如 TDD、安全审查或深度研究 | 任务需要时加载 |
| 代理 | 具有自身上下文和工具权限的限定范围工作者 | 隔离规划、实现和审查 |
| 规则 | 持久的项目或语言标准 | 始终加载，因此选择性安装 |
| 钩子 | 由工具链事件触发的脚本 | 在模型上下文之外运行 |
| 直觉 | 从真实会话中学习到的模式，带有置信度分数 | 相关时召回 |

### 在工具链之间共享上下文

ECC 的记忆保险库为 Claude、Codex、Hermes、OpenClaw、Kimi 及其他工具链提供一种本地、可检查的 Markdown 格式，用于持久上下文和交接。项目和团队记忆存放在 `.ecc/memory/` 下；用户记忆存放在 `~/.ecc/memory/` 下。

```bash
npm install -g ecc-universal
ecc memory init --scope project
ecc memory search "认证迁移" --target-harness codex
ecc memory doctor
```

记忆是未经审查的上下文，而非可执行策略。请对照权威来源验证重要声明，并将已接受的知识提升到受治理的项目文档中。可选的 `ecc-memory-mcp` 服务器暴露相同的受限保存、搜索、读取和诊断接口，但默认不启用。

[打开统一记忆工作流 →](skills/unified-memory/SKILL.md)

<details>
<summary><strong>记忆保险库深入：范围、交接和信任边界</strong></summary>

记忆保险库存储可移植的 `ecc.memory.v1` Markdown 文档，而不是复制供应商对话记录或在代理之间通过电子邮件发送上下文。项目记忆受失败关闭的 `.gitignore` 保护；仅将团队范围用于人工检查、版本控制的共享。团队记忆即使在提交后仍属于未经审查的上下文。

仅技能、最小化、手动和 Claude 插件安装不会将记忆保险库运行时放入 `PATH`。在使用 CLI 或可选 MCP 服务器之前，请单独安装 npm 运行时：

```bash
npm install -g ecc-universal
ecc memory --help
command -v ecc-memory-mcp
```

```bash
# 初始化项目保险库。
ecc memory init --scope project

# 将交接正文写入常规文件，然后针对下一个工具链。
ecc memory handoff \
  --from hermes \
  --target codex \
  --title "继续认证迁移" \
  --body-file ./handoff.md

# 从另一个工具链召回。
ecc memory search "认证迁移" --target-harness codex
ecc memory read <memory-id>

# 在共享团队记忆前验证保险库。
ecc memory doctor
```

记忆正文仅通过 `--stdin` 或 `--body-file` 接受，不作为命令行值。首个版本保持每个保险库条目未经审查且仅创建；人工审查将已接受的知识提升到受治理的项目文档中，而不是改变记忆信任。正常搜索召回返回活跃的项目和团队记忆。直接 ID 读取可以检查非活跃条目。用户范围召回必须显式请求。代理必须对照权威来源验证重要声明，绝不能将召回正文视为可执行指令或策略。

对于可选 MCP 访问，从 [`mcp-configs/mcp-servers.json`](mcp-configs/mcp-servers.json) 将 `ecc-memory-vault` 条目添加到每个需要它的工具链，然后运行 `ecc-memory-mcp`。服务器仅暴露 `memory_save`、`memory_search`、`memory_read` 和 `memory_doctor`。每个服务器必须以小写 `ECC_MEMORY_HARNESS` 身份启动；该身份绑定到服务器，不能由工具调用者提供。用户范围还需要操作员控制的 `ECC_MEMORY_ALLOW_USER_SCOPE=1` 选择加入。有关工作流和信任边界，请参阅 [`skills/unified-memory/SKILL.md`](skills/unified-memory/SKILL.md)；有关能力契约，请参阅 [`docs/design/ecc-memory-vault.md`](docs/design/ecc-memory-vault.md)。

</details>
